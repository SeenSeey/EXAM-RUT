1. Основы Spring Framework (IoC, DI, Beans).
Spring построен вокруг инверсии управления: жизненным циклом объектов и их связями управляет контейнер, а не код приложения. Благодаря этому классы зависят от абстракций и не создают свои зависимости сами - реализации проще заменять и подменять в тестах.
IoC (Inversion of Control) - принцип, при котором создание объектов и связывание зависимостей передаётся внешнему контейнеру. Код описывает, что ему нужно, а не как это создать.
DI (Dependency Injection) - конкретная реализация IoC: контейнер передаёт объекту его зависимости извне, через конструктор, сеттер или поле.
Bean - объект, которым управляет Spring-контейнер: создаёт, настраивает, внедряет и отслеживает его жизненный цикл.
ApplicationContext - сам контейнер, который хранит бины и выдаёт их по запросу.
Ключевые понятия:
Способы внедрения. 
Через конструктор - предпочтительный: зависимости обязательны, видны в сигнатуре, поле можно сделать final, а класс тестируется без контейнера. 
Через сеттер - для опциональных зависимостей.
Через поле (@Autowired на поле) - не рекомендуется: скрывает зависимости и мешает юнит-тестам.
Объявление бинов. 
Аннотации-стереотипы @Component, @Service, @Repository, @Controller со сканированием компонентов - для своих классов; 
@Bean-методы в @Configuration - для сторонних классов и явной настройки.
Область видимости (scope). 
singleton (по умолчанию - один экземпляр на контейнер), 
prototype (новый экземпляр на каждый запрос), 
а также веб-области request и session.
Жизненный цикл. Хуки @PostConstruct и @PreDestroy или интерфейсы InitializingBean/DisposableBean.
Проксирование. Для AOP (транзакции, безопасность) Spring оборачивает бины прокси - JDK-прокси по интерфейсу или CGLIB по классу. Это объясняет ряд неочевидных эффектов в разделах про Security и @Transactional.

Жизненный цикл контейнера: BeanDefinition, BFPP, BPP
Контейнер поднимается в две принципиально разные фазы: сначала собираются метаданные о бинах, и только потом создаются сами бины. Точки расширения привязаны к этим фазам, и их смешение - источник трудноуловимых ошибок.
BeanDefinition - метаданные, «рецепт» бина: класс, scope, зависимости, init/destroy-методы, lazy, primary, фабричный метод. Это не сам объект, а описание того, как его создать. Определения регистрируются в BeanDefinitionRegistry из аннотаций, JavaConfig или XML ещё до инстанцирования.
BeanFactoryPostProcessor (BFPP) - работает с уже загруженными BeanDefinition, но до создания бинов. Может править метаданные и добавлять новые определения. Примеры: PropertySourcesPlaceholderConfigurer (подстановка ${...}) и сам ConfigurationClassPostProcessor, который обрабатывает @Configuration, @Bean и @ComponentScan. Подтип BeanDefinitionRegistryPostProcessor умеет регистрировать новые определения программно.
BeanPostProcessor (BPP) - работает с уже созданными экземплярами, в двух точках вокруг инициализации: postProcessBeforeInitialization и postProcessAfterInitialization. Именно BPP создаёт AOP-прокси (AbstractAutoProxyCreator), обрабатывает @Autowired (AutowiredAnnotationBeanPostProcessor) и @PostConstruct (CommonAnnotationBeanPostProcessor). Прокси транзакций и Security рождаются здесь.

Остальные точки кастомизации контекста: Aware-интерфейсы (BeanNameAware, ApplicationContextAware - бин получает ссылки на инфраструктуру), ApplicationContextInitializer (до обновления контекста), события через ApplicationListener/@EventListener, FactoryBean (бин, создающий другой бин), а также хуки инициализации @PostConstruct и InitializingBean.
Главная идея: Контейнер владеет графом объектов, поэтому классы получают зависимости, а не конструируют их; практический вывод - внедряйте через конструктор, тогда зависимости обязательны, видны в сигнатуре и класс тестируется без поднятия контекста. Одним уровнем глубже полезно помнить, что контейнер работает в две фазы - сначала метаданные (BeanDefinition, BFPP), затем экземпляры (BPP), - и что AOP-прокси создаются именно на второй фазе. 

2. Spring Boot: создание и конфигурация приложений.
Spring Boot - это фреймворк, который помогает создавать автономные приложения на базе Spring, готовые к самостоятельному запуску. Он упрощает и ускоряет разработку, устраняя необходимость в долгой настройке. Основные механизмы Spring Boot:
стартеры — согласованные наборы зависимостей под типовые задачи;
автоконфигурация — автоматическое создание компонентов (бинов) с учётом содержимого classpath и условий;
встроенный (embedded) веб-сервер — контейнер запускается внутри процесса приложения (Tomcat, Jetty, Undertow или Netty в зависимости от стека).
Для создания нового проекта Spring Boot рекомендуется использовать веб-инструмент Spring Initializr: https://start.spring.io/.
Точка входа
@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}
Аннотация @SpringBootApplication три действия сразу:
@SpringBootConfiguration - конфигурационный класс Spring
@EnableAutoConfiguration - включить автоконфигурацию
@ComponentScan - поиск компонентов в пакете и ниже
Стартеры и состав зависимостей
Стартер — заранее подобранный комплект библиотек для конкретного сценария. Подключение одной зависимости в pom.xml или build.gradle (например, spring-boot-starter-web) приводит к тому, что при сборке и запуске нужные JAR оказываются доступны Java-машине (classpath — перечень библиотек, из которых приложение может загружать классы). Для starter-web на этот перечень попадают Spring MVC, Jackson и встроенный Tomcat (spring-boot-starter-tomcat).
Автоконфигурация
При вызове SpringApplication.run Spring Boot загружает перечень классов автоконфигурации. В Spring Boot 3 для этого используется механизм AutoConfiguration.imports в составе библиотек; в более ранних версиях применялся файл spring.factories. Каждый такой класс сопровождается условиями. При выполнении условий создаются соответствующие бины: фабрика веб-сервера, DispatcherServlet, DataSource и другие компоненты.
Логическая последовательность запуска:
стартер → библиотеки на classpath → проверка условий → создание бинов → запуск встроенного сервера.
Наиболее частые условия:
@ConditionalOnClass - на classpath присутствует указанный класс
@ConditionalOnMissingBean - одноимённый бин ещё не объявлен разработчиком
@ConditionalOnProperty - свойство конфигурации имеет требуемое значение
Благодаря этому значительная часть инфраструктуры создаётся без явного описания каждого бина. Для анализа включённых и отключённых автоконфигураций используют:
свойство debug=true и отчёт CONDITIONS EVALUATION REPORT в журнале;
endpoints Spring Boot Actuator (при наличии зависимости).
Поведение можно изменить объявлением собственного @Bean, исключением автоконфигурации через spring.autoconfigure.exclude либо настройкой свойств в файле конфигурации.
Выбор встроенного веб-сервера. При использовании spring-boot-starter-web приложение строится на servlet-стеке Spring MVC. Данный стартер по умолчанию зависит от spring-boot-starter-tomcat. После появления классов Tomcat на classpath автоконфигурация создаёт TomcatServletWebServerFactory, и при старте приложения поднимается встроенный Tomcat, который принимает HTTP-запросы на порту JVM-процесса.

Внешняя конфигурация приложения
Spring Boot отделяет параметры среды выполнения от исходного кода: одно и то же приложение может использовать различные URL базы данных, порты и флаги без изменения и пересборки кода. Значения читаются из внешней конфигурации. Форматы YAML и .properties эквивалентны по смыслу: YAML удобнее для иерархических структур, .properties задаёт те же ключи в плоском виде.
Профили (dev, test, prod) позволяют хранить общую конфигурацию и различия по средам. Активный профиль указывают через spring.profiles.active или переменную окружения SPRING_PROFILES_ACTIVE; поверх базового файла подключается, например, application-dev.yml.
Под «конфигурацией» в контексте Boot понимают прежде всего внешние свойства приложения и то, как автоконфигурация использует их при создании бинов. Так, наличие spring.datasource.url приводит к созданию и настройке DataSource.
Передача настроек в код - @Value и @ConfigurationProperties
Недостаточно указать, что параметры хранятся в application.yml: необходимо объяснить, каким образом они становятся доступны в коде.
Аннотация @Value("${ключ}") внедряет одно свойство (допустимо значение по умолчанию: ${ключ:Hello}). Способ удобен для отдельных параметров. При увеличении числа ключей строки разрозненно появляются в классах, усложняются групповая валидация и сопровождение.
Аннотация @ConfigurationProperties(prefix = "...") связывает целое дерево свойств с типом Java (в современной практике часто используют record). Например, префикс app.mail и поля host, port, enabled соответствуют блоку app.mail.* в YAML. За счет чего повышается типобезопасность, упрощается валидацию (@Validated, ограничения на поля) и документирование настроек; при подключении spring-boot-configuration-processor улучшаются подсказки в IDE.
Рекомендуемая практика: связанные параметры предметной области оформлять через @ConfigurationProperties; @Value оставлять для отдельных свойств. Секретные значения не следует хранить в открытом виде в репозитории — используют переменные окружения или средства управления секретами.
Явная конфигурация и способ поставки
Spring Boot не исключает классическую модель Spring. При необходимости нестандартной сборки определяют @Configuration и методы @Bean. Автоконфигурация, как правило, не создаёт конфликтующий бин, если сработало условие @ConditionalOnMissingBean.
Для развёртывания чаще формируют исполняемый JAR со всеми зависимостями. Упаковка в WAR для внешнего контейнера сохраняется как вариант, однако для типового сервиса на Spring Boot достаточно модели «JAR + встроенный сервер».

3. Spring MVC: обработка запросов, контроллеры, модели и представления.
DispatcherServlet: единая точка входа
Любой HTTP-запрос требует не только бизнес-логики, но и инфраструктурной работы: маршрутизации, конвертации параметров, обработки ошибок, формирования ответа. Чтобы не дублировать этот инфраструктурный код для каждого обработчика Spring MVC построен на паттерне Front Controller: все запросы приложения проходят через одну точку, где общая работа выполняется один раз, а затем делегируется «специалисту».
Роль этого Front Controller играет DispatcherServlet. Важно, что это именно сервлет: Spring не заменяет Servlet API, а встраивается в него. Контейнер (Tomcat) по-прежнему делает низкоуровневую работу - сеть, потоки, парсинг HTTP, - но вместо множества сервлетов в нём зарегистрирован один, спринговый, замапленный на все пути (/). Так Spring получает контроль над каждым запросом, оставаясь совместимым с любым стандартным контейнером.
DispatcherServlet сам почти ничего не умеет - он диспетчер. При старте он получает WebApplicationContext - IoC-контейнер Spring, и находит в нём своих помощников: кто ищет обработчик (HandlerMapping), кто его вызывает (HandlerAdapter), кто превращает имя представления в шаблон (ViewResolver), кто обрабатывает исключения. 
Почему не монолитный «умный» сервлет? Потому что у каждой задачи есть несколько разумных реализаций (маршрутизация по аннотациям или по конфигурации; представления на JSP, Thymeleaf, JSON...). Диспетчер реализует лишь алгоритм обработки, а каждый шаг - заменяемая стратегия. Именно поэтому фреймворк спокойно пережил переход от HTML-эпохи к REST.
HandlerMapping и контроллеры: кто обработает запрос
Все запросы стекаются в одну точку - значит, нужен механизм, который по данным запроса (путь, HTTP-метод) найдёт исполнителя. Это HandlerMapping. Без него пришлось бы либо писать гигантский switch по URL, либо регистрировать каждый путь в конфигурации. Spring выбрал декларативный путь: разработчик прямо на методе аннотацией объявляет «я обрабатываю такие запросы», а фреймворк при старте сканирует бины и собирает объявления в реестр. Знание о маршруте живёт рядом с кодом, который его обслуживает.
Так появляется контроллер - обычный Java-класс (POJO) с аннотацией @Controller, чьи методы помечены @GetMapping, @PostMapping и т.д. Он ничего не наследует и не зависит от Servlet API: его методы принимают и возвращают обычные Java-типы. Это осознанное решение - контроллер тестируется обычным юнит-тестом, а перевод «HTTP ↔ Java» вынесен во фреймворк.
HandlerAdapter: как вызвать метод с произвольной сигнатурой
Обработчик найден, но у диспетчера проблема: маппинг вернул ему объект типа Object. Spring принципиально не диктует, как выглядит обработчик: сигнатуры аннотированных методов свободные - show(@PathVariable long id, Model model), create(@RequestBody OrderDto dto) - общего интерфейса нет и быть не может. Именно HandlerAdapter позволяет обработчикам быть “какими угодно”.
Технически подготовка аргументов устроена как цепочка HandlerMethodArgumentResolver-ов: адаптер смотрит на тип и аннотации каждого параметра и для каждого находит резолвер, умеющий с ним работать. @PathVariable long id - из пути с конвертацией в long; @RequestParam - из query string; Model - создаётся новая; @RequestBody - десериализация тела. Список расширяем: можно написать свой резолвер и внедрять, например, текущего пользователя одной аннотацией.
Model: данные отдельно от отображения
Метод отработал - как превратить данные в ответ? Здесь работает паттерн из названия фреймворка: у ответа две независимые составляющие - что показывать (данные) и как показывать (оформление), и смешивать их нельзя, иначе вёрстку не изменить без программиста, а данные не переиспользовать для другого формата.
Model - именованный контейнер данных, который контроллер наполняет, а представление читает. Контроллер сказал «вот заказ под именем order» - и его ответственность закончилась; он не знает, станет ли заказ HTML-страницей или PDF. Контроллер и шаблон связаны только именами атрибутов.
После вызова метода адаптер упаковывает результат в ModelAndView - пару «данные + имя представления». 
ViewResolver и View: от имени к готовому ответу
Представление в ModelAndView задано логическим именем ("order-details"), а не путём к файлу - иначе контроллер был бы привязан к технологии шаблонов, и смена Thymeleaf на Freemarker потребовала бы править все контроллеры. Перевод имени в шаблон - задача стратегии ViewResolver: по имени она возвращает объект View, чья единственная обязанность - взять модель и записать готовый ответ в HttpServletResponse.
REST: @ResponseBody и HttpMessageConverter
Современные приложения чаще отдают не HTML, а данные в JSON.  Аннотация @ResponseBody сообщает адаптеру, что возвращаемое значение - не имя представления, а само содержимое ответа, которое нужно сериализовать. Сериализацией занимается ещё одна цепочка стратегий - HttpMessageConverter. Симметрично @RequestBody десериализует тело запроса на входе. Сокращение @RestController = @Controller + @ResponseBody на всех методах:
Обработка исключений
Если метод контроллера бросил исключение, диспетчер не даёт ему улететь в контейнер, а передаёт цепочке HandlerExceptionResolver-ов. Инструмент разработчика - @ExceptionHandler.
Полный путь запроса
Проследим жизнь запроса GET /api/orders/42:
1) Tomcat парсит HTTP и вызывает единственный сервлет - DispatcherServlet.
2) Диспетчер опрашивает HandlerMapping-и - реестр аннотаций находит HandlerMethod (OrderRestController.get) и вынимает 42 из шаблона пути.
3) Диспетчер подбирает HandlerAdapter; тот через резолверы готовит аргументы (@PathVariable long id → 42L) и вызывает метод, который возвращает OrderDto. 
4) Дальше развилка: при @ResponseBody объект уходит в HttpMessageConverter, и Jackson пишет JSON (в классическом сценарии был бы ModelAndView → ViewResolver → View.render() → HTML). 
5) Исключение на любом шаге перехватывает цепочка ExceptionResolver-ов и @ExceptionHandler. Готовый ответ возвращается контейнеру и уходит клиенту.

4. Работа с базами данных: Spring Data JPA, Hibernate.
Доступ к БД в Spring строится на трёх слоях, и различать их важно - именно на их стыке возникает большинство проблем.
ORM (object-relational mapping) - подход, при котором объекты предметной области отображаются на строки таблиц, чтобы работать с данными как с объектами, а не писать SQL вручную.
JPA (Jakarta Persistence API) - стандарт ORM для Java: набор интерфейсов и аннотаций (@Entity, @Id, EntityManager). Это спецификация - сама она ничего не выполняет.
Hibernate - самая распространённая реализация JPA: генерирует SQL, ведёт кэш и отслеживает изменения сущностей.
Spring Data JPA - надстройка Spring над JPA: убирает шаблонный код доступа к данным, превращая интерфейс-репозиторий в готовую реализацию.

	Сущности и репозитории
Сущности. Класс помечается @Entity, поле-идентификатор - @Id и @GeneratedValue, связи - @OneToMany, @ManyToOne, @ManyToMany. В Spring 6 / Boot 3 аннотации живут в пространстве имён jakarta.persistence (раньше - javax.persistence).
Репозитории. Интерфейс, наследующий JpaRepository, даёт CRUD «из коробки». Методы-запросы выводятся из имени (findByEmailAndActiveTrue), сложные пишутся через @Query (JPQL или нативный SQL). Поддерживаются пагинация и сортировка (Pageable).
Стратегия загрузки. FetchType.LAZY откладывает загрузку связи до обращения, EAGER грузит сразу. По умолчанию коллекции ленивы, а @ManyToOne - жадный.

Контекст персистентности
Между вызовом репозитория и коммитом сущности живут в контексте персистентности (persistence context) - он же кэш первого уровня. Hibernate не пишет в БД на каждое изменение: он накапливает правки и синхронизирует их при flush. Из этого write-behind растут и удобство (dirty checking без явного save), и типичные проблемы - от N+1 до LazyInitializationException.

Кэш первого уровня и dirty checking. Контекст (кэш L1) хранит managed-сущности и при flush сравнивает их с исходным снимком - изменённые синхронизируются без явного save. Flush происходит перед запросами (режим AUTO) и на коммите, а не в момент изменения (write-behind).
readOnly = true переводит Hibernate в FlushMode.MANUAL: снимки и dirty checking пропускаются, лишних UPDATE нет - заметная оптимизация для чтения.
Кэши. L1 - всегда, на контекст; L2 - опциональный, на SessionFactory (Ehcache/Infinispan/Hazelcast); отдельно query cache. L2 требует осторожности с инвалидацией.
Генерация идентификаторов. IDENTITY отключает пакетную вставку - Hibernate обязан получить сгенерированный id сразу после каждого INSERT. SEQUENCE с оптимизаторами (pooled/pooled-lo) позволяет батчить и экономит обращения к последовательности.
Репозитории Spring Data - это прокси-реализации поверх SimpleJpaRepository, создаваемые JpaRepositoryFactory. Имена методов парсятся в запросы; сложное - через @Query (JPQL/native), Specification/Criteria или QueryDSL.

Из этой механики вытекают типичные ошибки
N+1 и его лечение: JOIN FETCH, @EntityGraph, @BatchSize, subselect. При попытке JOIN FETCH двух коллекций-списков - MultipleBagFetchException (лечится Set или раздельными запросами).
LazyInitializationException - обращение к ленивой связи после закрытия контекста (вне транзакции). Загружайте нужные данные внутри транзакции, а не расширяйте её границы «на всякий случай».
Open Session In View. В Spring Boot по умолчанию включён и держит контекст открытым до рендеринга ответа, пряча LazyInitializationException ценой удержания соединения. Многие команды его отключают ради явных границ транзакции.
save() в Spring Data для не-нового объекта делает merge, а тот при отсутствии сущности в контексте выполняет лишний SELECT. Для новых используйте persist-семантику (Spring определяет «новизну» по @Id/Persistable.isNew()).
DTO-проекции вместо загрузки полных сущностей - конструкторные выражения в JPQL или интерфейсные проекции; для чтения это дешевле и не тянет связи.
Блокировки: оптимистичная через @Version (защита от lost update), пессимистичная через LockModeType.PESSIMISTIC_WRITE.
equals/hashCode сущностей нельзя строить на генерируемом @Id (он null до вставки) - используйте бизнес-ключ или заранее присвоенный UUID.
Батч-обработка: включите hibernate.jdbc.batch_size, order_inserts/order_updates и периодически flush()+clear(), иначе контекст растёт и съедает память.

	Главная идея: три слоя делят ответственность - JPA задаёт стандарт, Hibernate его исполняет, Spring Data убирает шаблонный код. Но работает всё не «по вызову save», а по границам контекста персистентности: flush перед запросами и на коммите, dirty checking по снимку. Держите транзакции короткими, для чтения ставьте readOnly, отдавайте DTO вместо сущностей и заранее закрывайте N+1 - тогда ORM экономит код, не пряча дорогие запросы.

5. RESTful API: создание и документирование (Swagger/OpenAPI).
REST (Representational State Transfer) - архитектурный стиль проектирования сетевых приложений на основе модели «клиент - сервер». Сервер предоставляет ресурсы, клиент их запрашивает и изменяет. Каждый ресурс обозначается адресом URI, а текущее состояние ресурса передаётся в том или ином представлении - на практике чаще всего в формате JSON. 
К основным идеям REST обычно относят следующее.
Ресурсы и URI. Логическая единица API - не «процедура», а ресурс. Адрес должен однозначно указывать, с каким объектом или набором объектов работает клиент.
Единообразный интерфейс через HTTP. Операции выражают стандартными методами протокола (GET, POST, PUT, PATCH, DELETE и др.), а исход - стандартными кодами ответа.
Отсутствие состояния на сервере (stateless). Между запросами сервер не обязан хранить «сессию диалога» с клиентом. Каждый запрос содержит всё необходимое для обработки.
Разделение клиента и сервера - развиваются независимо, взаимодействуя только через контракт API.
GET - получение одного ресурса или коллекции. Метод безопасный и идемпотентный. Фильтры, сортировку и пагинацию обычно передают в строке запроса (?author=Bloch&page=0&size=20).
POST - в типичном CRUD означает создание нового ресурса: клиент отправляет данные, сервер сохраняет объект и, как правило, возвращает его уже с идентификатором. Повтор того же POST часто создаёт второй объект, поэтому метод не считают идемпотентным. Кроме создания POST иногда используют для запуска операции, которую трудно представить отдельным ресурсом (отправка письма, старт пересчёта, формирование отчёта).
PUT - полная замена ресурса по указанному URI. Клиент присылает целое состояние; то, чего нет в теле, по контракту API обычно считают отсутствующим или сброшенным. Метод небезопасный, но идемпотентный: повтор того же PUT должен оставить ресурс в том же виде.
PATCH - частичное изменение: обновляют отдельные поля, не пересылая весь объект. Это удобно для больших моделей. Идемпотентность зависит от семантики конкретного «патча», но при аккуратной реализации повтор того же изменения не должен порождать лишних эффектов.
DELETE - удаление ресурса. Метод идемпотентный в том смысле, что повторное удаление уже отсутствующего объекта не создаёт новое состояние «ещё более удалённого» ресурса.
HEAD и OPTIONS используют реже: HEAD подобен GET без тела ответа, OPTIONS сообщает допустимые методы (в том числе в сценариях CORS).
QUERY - относительно новый метод, задуманный как безопасное чтение с телом запроса, когда фильтр слишком сложен для URI. Поддержка в инструментах пока не повсеместна; в реальных Spring MVC-сервисах по-прежнему чаще применяют GET с query-параметрами или, иногда, отдельный поиск через POST 
Не любой сервис обязан реализовывать полный набор методов. В прикладных системах иногда ограничиваются GET и POST, если обновления редки или изменение моделируют созданием новой версии; Сводить все операции к одному POST с «командами» в теле технически возможно, но это уже ближе к RPC, чем к REST: хуже используется кэширование, API труднее читать по адресам и методам, слабее стыкуются документация и типовые API-шлюзы.
Проектирование URI
Адрес должен называть ресурс -  то есть объект или коллекцию объектов, — а действие над ним передавать HTTP-методом. Поэтому в path предпочитают имена сущностей во множественном числе (/books, /orders), а не слова, обозначающие действие («получить», «создать», «удалить»). 
К типовым ошибкам относят нестабильное число имени (/book рядом с /books), излишне глубокую вложенность без необходимости, а также рассогласование идентификатора в URI и в теле запроса. Умеренная вложенность вида GET /users/5/orders допустима, если заказы действительно принадлежат пользователю. Фильтры и пагинацию выносят в query-параметры. При длительном жизненном цикле API часто вводят префикс и версию: /api/v1/.... В path используют нижний регистр; составные слова при необходимости разделяют дефисом (/order-items).
Реализация в Spring Boot
Типичный REST-сервис на Spring Boot развивают по слоям. Сначала описывают модель данных или, что предпочтительнее для внешнего контракта, отдельный DTO. Затем создают контроллер с аннотацией @RestController - он принимает HTTP-запросы. Бизнес-правила выносят в @Service, а работу с базой данных - в репозиторий. Контроллер остаётся тонкой границей: разобрать запрос, вызвать сервис, вернуть ответ.
Аннотация @RestController объединяет @Controller и @ResponseBody. Это означает, что возвращаемое значение метода не интерпретируется как имя HTML-шаблона, а становится телом HTTP-ответа.
Обработка запроса в Spring MVC идет так. Запрос поступает в DispatcherServlet и направляется в метод контроллера. После того как метод вернул Java-объект (например, BookDto), Spring подбирает подходящий HttpMessageConverter - компонент, который умеет преобразовать объект в байты ответа с нужным Content-Type либо, наоборот, прочитать тело запроса в объект. Для JSON в типичном приложении на spring-boot-starter-web используется конвертер на основе библиотеки Jackson (MappingJackson2HttpMessageConverter): он сериализует поля объекта в JSON и десериализует JSON из @RequestBody обратно в Java-тип.
Если представление в JSON ведёт себя неожиданно (даты, циклические ссылки, ленивые коллекции JPA), настраивают Jackson или отдают наружу отдельные DTO без инфраструктурных деталей persistence-слоя.
Если метод возвращает DTO напрямую, Spring по умолчанию отвечает кодом 200 OK и сериализованным телом. Класс ResponseEntity<T> нужен, когда необходимо явно задать статус, заголовки или отсутствие тела. Хорошей практикой считают единый стиль ответов, вынесение ошибок в @ControllerAdvice и использование кодов 4xx/5xx для неуспешных исходов, а не «200 OK с текстом ошибки в теле». К антипаттернам относят постоянный 200 вне зависимости от результата, отдачу наружу сущностей JPA с неинициализированными ленивыми связями и возврат null вместо осмысленного статуса.
Документирование API: OpenAPI и Swagger
Документация API нужна для согласованной работы фронтенда, смежных сервисов и внешних потребителей. OpenAPI Specification (OAS) - языконезависимый стандарт описания HTTP API в формате YAML или JSON: пути, методы, параметры, схемы тел запросов и ответов, коды статусов. Ранее ту же спецификацию часто называли Swagger Specification. Под Swagger обычно имеют в виду экосистему инструментов вокруг OpenAPI: редактор спецификаций, интерактивный Swagger UI, генераторы клиентского и серверного кода.
В проектах на Spring Boot 3 для генерации OpenAPI и подключения UI используют библиотеку springdoc-openapi. После добавления стартера вида springdoc-openapi-starter-webmvc-ui и запуска приложения описание контракта обычно доступно по пути /v3/api-docs, а интерфейс - через Swagger UI (точный URL зависит от версии и свойств springdoc.*). Описание уточняют аннотациями (@Operation, @Tag, @Schema и др.) либо ведут во внешнем файле спецификации.
Способ появления спецификации влияет на то, как команда проектирует API.
При подходе code-first сначала пишут контроллеры и модели, а OpenAPI-документ генерируют из кода (как делает springdoc). Это ускоряет старт и хорошо подходит внутренним сервисам одной команды, но контракт может меняться вместе с реализацией, поэтому для внешнего API нужна дисциплина ревью изменений.
При подходе design-first, сначала согласуют и фиксируют OpenAPI-контракт, а сервер и клиенты реализуют уже по нему (иногда с генерацией заготовок кода). Контракт становится точкой согласования для заказчика и смежных команд до начала активной разработки, проще отслеживать несовместимые изменения. Цена подхода - более высокий входной порог и необходимость следить, чтобы код не разошёлся со спецификацией.
Независимо от подхода полезно версионировать API, не ломать существующие поля без новой версии, единообразно описывать ошибки.
6. Spring Security: аутентификация и авторизация.
Spring Security - это главный фреймворк для защиты приложений на платформе Spring. Он отвечает за:
Аутентификацию (Authentication) - проверку личности пользователя (логин/пароль, OAuth2-токен, JWT).
Авторизацию (Authorization) - проверку прав доступа: что конкретный пользователь может делать в системе.
Защиту от атак: CSRF (подделка запросов), session fixation (фиксация сессии), clickjacking, brute-force и т. д.

1 Архитектура Spring Security
1.1. Ключевые элементы
DelegatingFilterProxy - точка входа в Spring Security из контейнера сервлетов (Tomcat, Jetty и т. д.).
FilterChainProxy - управляет списком фильтров.
SecurityFilterChain - конфигурация безопасности для конкретного набора URL (например, /api/** защищается через JWT, а /login работает через форму).
AuthenticationManager - главный менеджер, который отвечает за аутентификацию. Он делегирует проверку конкретным провайдерам (AuthenticationProvider).
UserDetailsService - интерфейс, который загружает информацию о пользователе из БД (логин, пароль, роли).
PasswordEncoder - отвечает за хэширование и проверку паролей (BCrypt и т. д.).
SecurityContext - объект, где хранится информация о текущем пользователе (Authentication).
1.2. Пример реальной цепочки фильтров
В приложении с формой логина Spring Security строит цепочку фильтров, которая включает:
SecurityContextPersistenceFilter - загружает данные о пользователе из сессии.
CsrfFilter - проверяет CSRF-токен.
UsernamePasswordAuthenticationFilter - перехватывает POST /login, проверяет логин/пароль.
BasicAuthenticationFilter - обрабатывает заголовок Authorization: Basic ....
BearerTokenAuthenticationFilter - проверяет JWT или OAuth2-токен.
AnonymousAuthenticationFilter - если пользователь не залогинен, присваивает ему "анонимную" роль.
ExceptionTranslationFilter - обрабатывает ошибки безопасности.
FilterSecurityInterceptor - финальная проверка прав на доступ.
1.3. Servlet vs Reactive
– Servlet (Tomcat/Jetty/Undertow): используется классическая цепочка фильтров (Filter).
–Reactive (WebFlux/Netty): применяется WebFilter, SecurityWebFilterChain, реактивный ReactiveAuthenticationManager. Отличие - контекст безопасности хранится в reactive context, а не в ThreadLocal.

2 Аутентификация и Авторизация
2.1. Аутентификация (Authentication)
Аутентификация = процесс проверки личности пользователя. Spring Security отвечает на вопрос: кто выполняет запрос?
Основные сценарии:
– Форма логина (Form Login).
– Пользователь отправляет POST /login с username и password.
– UsernamePasswordAuthenticationFilter перехватывает запрос.
– AuthenticationManager вызывает DaoAuthenticationProvider.
– UserDetailsService ищет пользователя в БД.
– PasswordEncoder сверяет пароль (BCrypt, Argon2).
– Если проверка успешна → создаётся объект Authentication, который сохраняется в SecurityContext.
– HTTP Basic
– Запрос содержит Authorization: Basic base64(user:password).
– Применяется в простых REST API (только через HTTPS).
– JWT (Bearer Token)
– В заголовке: Authorization: Bearer <jwt>.
– Токен проверяется (exp, iss, aud, подпись).
– Если валидный → создаётся Authentication.
– Stateful-сессий нет, каждая проверка независимая.
– OAuth2 / OpenID Connect
– Пользователь логинится через внешнего провайдера (Google, GitHub).
– Spring Security получает access token / id token.
– Ресурсный сервер (resource server) проверяет токен (обычно JWT).
2.2. Авторизация (Authorization)
Авторизация = проверка прав доступа. Spring Security отвечает: какие действия разрешены?
Уровни:
1 URL-уровень
В конфигурации HttpSecurity:
http.authorizeHttpRequests(auth -> auth
   .requestMatchers("/admin/**").hasRole("ADMIN")
   .requestMatchers("/user/**").hasAnyRole("USER", "ADMIN")
   .anyRequest().authenticated()
);
/admin/** доступен только ADMIN, /user/** доступен USER и ADMIN, остальные URL требуют аутентификации.
2 Методный уровень
Используются аннотации в сервисах:
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) { ... }
Таким образом проверка может быть завязана не только на роли, но и на бизнес-логику.
3 Доступ на уровне доменных объектов (ACL)
Используется AclService и PermissionEvaluator.
Пример: только автор статьи может её редактировать.

3 Жизненный цикл запроса в Spring Security
Общая последовательность:
1. Клиент (браузер, мобильное приложение, другой сервис) → отправляет запрос (GET/POST/PUT и т. д.).
2. Запрос попадает на сервер (Tomcat/Jetty/Undertow).
3. Контейнер запускает цепочку фильтров (Filter Chain).
4. Среди фильтров есть DelegatingFilterProxy, который передаёт управление в Spring Security.
5. Запрос проходит через серию фильтров Spring Security.
6. Если аутентификация и авторизация успешные → запрос доходит до контроллера.
7. Контроллер выполняет логику и возвращает ответ.
8. Ответ снова проходит через фильтры (часть данных сохраняется в сессию, добавляются заголовки безопасности).


4 Stateful vs Stateless (сессии и JWT)
4.1. Stateful (с состоянием, через сессии)
Как работает:
Пользователь проходит аутентификацию (например, через форму).
Сервер проверяет логин/пароль.
При успешной аутентификации сервер сохраняет информацию о пользователе в HttpSession. (Это объект в памяти сервера. В нём хранится SecurityContext с Authentication.)
Клиенту отправляется cookie (JSESSIONID).
При каждом запросе клиент передаёт cookie, сервер по нему восстанавливает пользователя из сессии.
Пример:
  – Первый вход → POST /login
  – Ответ сервера → Set-Cookie: JSESSIONID=abc123
  – Дальнейшие запросы → Cookie: JSESSIONID=abc123

Когда выбирать Stateful
Используется, когда важны контроль, безопасность и возможность мгновенно управлять сессиями. Например:
Пользователь сменил пароль → все сессии сразу инвалидируются.
Или
Администратор заблокировал пользователя → доступ прекращается мгновенно.
Плюсы: простой logout; можно завершить все сессии; легко ограничить количество устройств; можно отслеживать активные устройства.
Минусы: нужен Redis/DB; каждый запрос требует обращения к хранилищу; сложнее горизонтально масштабировать.

4.2. Stateless (без состояния, через JWT или токены)
Как работает:
Пользователь аутентифицируется (или получает токен через OAuth2).
Сервер не хранит состояние в памяти.
Клиент получает JWT (JSON Web Token).
JWT хранится на стороне клиента (localStorage, secure cookie, mobile keystore).
При каждом запросе клиент передаёт заголовок: Authorization: Bearer <jwt-token>
 Сервер проверяет токен (подпись, срок действия, права).
JWT структура
JWT состоит из трёх частей (разделённых точками): header.payload.signature
    Header → алгоритм подписи (например, HS256).
    Payload → данные: sub (user id), roles, exp (срок жизни).
    Signature → проверка подлинности (HMAC или RSA).

Когда выбирать Stateless
Используется, когда важны масштабируемость и высокая производительность.
Плюсы: нет центрального хранилища сессий; легко масштабируется на сотни серверов; идеально подходит для Kubernetes; минимальная задержка.
Минусы: logout не мгновенный; сложно отзывать токены; приходится использовать Refresh Token Rotation или Blacklist.

 7. Работа с транзакциями: аннотация @Transactional.
 Транзакция - набор операций с БД, выполняемых как единое целое: либо применяются все, либо ни одной. Это свойство описывают аббревиатурой ACID: 
atomicity (атомарность) - всё или ничего, 
consistency (согласованность) - переход между корректными состояниями,
isolation (изолированность) - параллельные транзакции не мешают друг другу
durability (долговечность) - после коммита данные сохранены даже при сбое.
@Transactional задаёт границы транзакции декларативно: вместо ручных begin/commit/rollback вы помечаете метод, а Spring открывает транзакцию перед его вызовом и коммитит или откатывает после.

 Использование
Где ставить. Обычно на методах сервисного слоя. На уровне класса аннотация применяется ко всем его public-методам.
Поведение по умолчанию. Коммит при успешном завершении, откат при RuntimeException или Error.
Декларативно или программно. @Transactional - декларативный путь; TransactionTemplate или прямой вызов PlatformTransactionManager - программный, когда нужен тонкий контроль над границами.
Основные параметры. propagation (поведение относительно активной транзакции), isolation (уровень изоляции), readOnly (оптимизация чтения), rollbackFor/noRollbackFor (правила отката), timeout.

За удобной аннотацией стоят прокси и привязка ресурса к потоку - из этого следуют все её особенности.

Механика
	TransactionInterceptor (advice на прокси) вызывает getTransaction() у PlatformTransactionManager. Менеджер берёт ресурс (Connection/EntityManager), стартует транзакцию и связывает ресурс с текущим потоком через TransactionSynchronizationManager, который хранит ресурсы в ThreadLocal. Дальше код в этом же потоке через DataSourceUtils/EntityManagerFactoryUtils получает тот же ресурс. По завершении - commit или rollback и отвязка ресурса.
	Какой менеджер под капотом:

	Прямое следствие привязки к потоку: транзакционный контекст не переходит на другой поток. При @Async, ручном создании потоков или в реактивных цепочках он не наследуется - реактивный стек использует не ThreadLocal, а контекст Reactor.
Propagation - поведение относительно активной транзакции потока:

присоединиться к активной или создать новую

Isolation делегируется соединению (setTransactionIsolation) и защищает от аномалий: грязное чтение, неповторяемое чтение, фантомы. Уровни - от READ_COMMITTED до SERIALIZABLE; по умолчанию наследуется от БД.
Правила отката. По умолчанию - только на RuntimeException/Error; на checked-исключения отката нет (нужен rollbackFor). Если внутренняя REQUIRED-транзакция помечена rollback-only, а внешняя пытается коммитить - UnexpectedRollbackException.
Пост-коммит хуки. TransactionSynchronization (afterCommit/afterCompletion) и @TransactionalEventListener(phase = AFTER_COMMIT) - чтобы, например, отправлять событие только после успешного коммита, а не внутри транзакции.

	Типичные ошибки:
Самовызов - вызов @Transactional-метода из того же класса идёт мимо прокси, транзакции нет.
Только public-методы перехватываются прокси Spring.
Checked-исключения не откатывают транзакцию по умолчанию.
catch внутри метода проглатывает исключение - отката не будет, хотя данные уже могли быть испорчены.
Длинные транзакции держат соединение из пула - источник деградации под нагрузкой.
В тестах @Transactional по умолчанию откатывает - удобно, но маскирует ошибки, видимые только на реальном коммите (например, отложенные констрейнты).

Главная идея: @Transactional объявляет границы ACID-транзакции, но реализован как прокси плюс ресурс в ThreadLocal, и из этого следует всё: самовызов и non-public не перехватываются, откат по умолчанию только на unchecked, контекст не переходит на другой поток, а REQUIRES_NEW удерживает два соединения. Держите транзакции короткими, задавайте rollbackFor для checked-исключений, а побочные эффекты вроде отправки событий вешайте на AFTER_COMMIT.

8. Кэширование в Spring: аннотация @Cacheable.
Кэширование - сохранение результата дорогого вычисления или запроса, чтобы при повторном обращении с теми же входными данными не выполнять работу заново, а вернуть готовый ответ. Обратная сторона - риск устаревания: после изменения в БД кэш может отдавать старое значение. Поэтому вместе с записью в кэш нужна инвалидация (обновление или удаление записи).
Spring не встраивает Redis или другую конкретную технологию прямо в аннотации. Вместо этого есть абстракция кэширования: бизнес-код помечает методы (@Cacheable и др.), а доступ к хранилищу идёт через интерфейсы Cache и CacheManager. Реализацию хранилища подставляют конфигурацией - от простой ConcurrentHashMap в памяти процесса до Caffeine или Redis. Благодаря этому один и тот же сервисный метод можно сначала обкатать на локальном кэше, а в проде перевести на распределённый, почти не меняя аннотации.
Чтобы механизм заработал, кэширование нужно включить - обычно аннотацией @EnableCaching на классе конфигурации. В Spring Boot рядом часто подключают spring-boot-starter-cache. Если разработчик не объявил свой бин CacheManager, Boot пытается выбрать провайдер по наличию библиотек на classpath либо поднимает простую реализацию в памяти. Тип можно задать явно (spring.cache.type).
Дальше важна модель вызова. Когда на классе сервиса есть методы с @Cacheable, Spring подставляет вместо «голого» объекта обёртку - прокси. Любой другой бин в приложении держит ссылку именно на эту обёртку.
Допустим, контроллер вызывает сервис так: catalogService.getItem(42). Запрос сначала попадает в прокси. Прокси вычисляет ключ кэша, спрашивает CacheManager, и только при промахе вызывает настоящий метод сервиса, после чего сохраняет результат. Именно прокси обрабатывает @Cacheable; сам класс сервиса про кэш «не знает».
Если же внутри самого CatalogService один метод вызывает другой через this.getItem(42), обращение идёт напрямую к объекту, минуя прокси. Аннотация не срабатывает: кэш не читается и не заполняется. Поэтому рассчитаны вызовы извне бина (контроллер → сервис), а не внутренние вызовы через this.
Кратко цепочка выглядит так: @EnableCaching регистрирует поддержку cache-advice → при вызове через прокси срабатывает interceptor → по имени кэша и ключу выполняется hit (попадание) / miss (промах) → при необходимости вызывается метод и результат кладётся в хранилище, выбранное CacheManager.
@Cacheable("items")
public ItemDto getItem(long id) {
    return itemRepository.findById(id).map(ItemMapper::toDto).orElseThrow();
}
"items" - имя кэша (отдельное пространство записей). Ключ по умолчанию строится из параметров метода; при необходимости задают SpEL: key = "#id".
Дополнительно:
condition — кэшировать ли вызов (проверка до метода);
unless — не класть в кэш некоторый результат (например null).
@Cacheable уместна на методах чтения, где повтор с теми же аргументами должен давать тот же ответ, пока данные не изменились.
Аннотация
Поведение
@CachePut
метод всегда выполняется, результат пишется в кэш 
(удобно после update)

удаляет запись или весь кэш (allEntries = true)

Важно! Без @CacheEvict / @CachePut после изменения в БД @Cacheable продолжит отдавать устаревшие данные.
Типичные ошибки
Вызов через this в том же классе. метод с @Cacheable вызывают из соседнего метода того же сервиса. Прокси не участвует и создаётся впечатление, что «аннотация не работает». Решение: вынести кэшируемый метод в другой бин или вызывать сервис извне (из контроллера / другого сервиса).
Забыли инвалидацию. На чтение повесили @Cacheable, а на update/delete не добавили @CachePut или @CacheEvict. В БД данные уже новые, API продолжает отдавать старые из кэша. 
Неудачный ключ. Если ключ слишком общий (игнорирует важный параметр), разные ответы схлопываются в одну запись. Если ключ слишком детальный (включает лишнее), попаданий почти не будет, и кэш не даст эффекта. Ключ должен однозначно соответствовать смыслу результата.
Кэширование сущностей JPA. В кэш кладут @Entity с ленивыми связями. При сериализации или повторном использовании вне сессии Hibernate возникают LazyInitializationException, циклы ссылок, раздувание памяти. Надёжнее кэшировать DTO или проекции.
Локальный кэш при нескольких инстансах. Сервис масштабируют на несколько подов, у каждого свой in-memory кэш. Один узел обновил данные и почистил свой кэш, соседний всё ещё отдаёт старое. Для такой схемы нужен общий (распределённый) кэш либо согласованная политика сброса.
Кэшируют то, что нельзя или незачем. Например без TTL данные, которые должны быть строго актуальны на каждый запрос, либо ответы, уникальные для почти каждого вызова: места в кэше заняты, пользы мало.

9. Конфигурация приложения: application.properties и application.yml.
Конфигурация - это набор параметров, которые определяют поведение приложения без изменения его кода. Главная идея заключается в разделении логики и настроек.

application.properties
Это классический формат конфигурации Spring Boot. Каждая настройка представляет собой пару ключ = значение.
server.port=8080
spring.datasource.url=jdbc:postgresql://localhost:5432/shop
spring.datasource.username=postgres
spring.datasource.password=12345
Плюсы: Максимально прост, сложно ошибиться в синтаксисе, отлично подходит для небольших микросервисов.
Минусы: Огромный уровень дублирования (избыточности). Если у вас 20 настроек для базы данных, вы 20 раз напишете префикс spring.datasource....

application.yml
YAML (или YML) использует древовидную структуру, где вложенность определяется пробелами (отступами).
server:
 port: 8080


spring:
 datasource:
   url: jdbc:postgresql://localhost:5432/shop
   username: postgres
   password: 12345
Плюсы: Наглядность, отсутствие дублирования, идеален для сложных, ветвистых конфигураций.
Минусы: Чувствителен к пробелам (один лишний пробел или использование Tab вместо пробела - и приложение не запустится).
Как Spring Boot использует эти файлы?
При запуске приложения Spring Boot автоматически ищет файл: application.properties или application.yml из каталога resources.
Во время старта он: считывает конфигурацию; создаёт объект настроек; использует их для настройки встроенного сервера, базы данных, логирования и других компонентов.

Механизм профилей (Profiles)
В реальной жизни вам постоянно нужно переключать настройки. На локальной машине база данных крутится в Docker без пароля, а на "проде" - это защищенный кластер. Для этого используются профили (Profiles).
Вы можете создать несколько файлов конфигурации:
    application-dev.yml - для разработки.
    application-prod.yml - для прода.
А в основном файле application.yml вы просто указываете, какой профиль сейчас активен:
spring:
 profiles:
   active: dev # На проде мы заменим это значение на prod

Кто и когда ищет эти файлы?
Когда ты запускаешь SpringApplication.run(MyApplication.class, args):
1 Создается объект SpringApplicationRunListeners, который объявляет о стадиях запуска приложения.
2 На этапе ApplicationEnvironmentPreparedEvent (окружение подготовлено, но контекст еще не создан) в игру вступает специальный механизм - EnvironmentPostProcessor.
3 Начиная со Spring Boot 2.4, за импорт файлов конфигурации отвечает класс ConfigDataEnvironmentPostProcessor. (Именно этот класс запускает поиск конфигурационных файлов по стандартным путям)
Парсинг: превращение текста в PropertySource
Spring Boot не работает напрямую с YAML или Properties в процессе работы приложения. Его цель - привести всё к единому плоскому виду "ключ-значение" и сохранить это в объект Environment (окружение).
Для этого используются специальные загрузчики - реализации интерфейса PropertySourceLoader:
    – PropertiesPropertySourceLoader - отвечает за .properties и .xml. Он парсит файлы построчно.
    – YamlPropertySourceLoader - отвечает за .yml и .yaml.
В результате парсинга создаются объекты PropertySource (источник свойств), которые регистрируются в едином реестре внутри Environment.

Иерархия и приоритеты
А если в проекте лежат и application.properties, и application.yml одновременно?
Spring Boot загрузит оба файла. Но так как PropertiesPropertySourceLoader и YamlPropertySourceLoader добавляют свои PropertySource в определенном порядке, application.properties имеет более высокий приоритет, чем application.yml, и перепишет его значения при совпадении ключей.

10. Тестирование и логирование.
Тесты фиксируют поведение кода и защищают от регрессий при изменениях. Их принято располагать пирамидой: много быстрых модульных тестов внизу, меньше интеграционных посередине и совсем немного сквозных наверху - чем выше уровень, тем тест дороже, медленнее и хрупче.
Модульные (unit). Проверяют один класс в изоляции, без контекста Spring; зависимости заменяются моками (Mockito). Быстрые, их большинство.
Интеграционные. Проверяют взаимодействие компонентов с поднятым контекстом Spring и, при необходимости, реальной БД.
Срезовые (slice). Промежуточный вариант Spring Boot: поднимается только нужный срез контекста, а не всё приложение.

	Основные инструменты:
JUnit 5 (Jupiter) - базовый фреймворк запуска тестов.
Mockito - моки и стабы: @Mock, @InjectMocks, when(...)/verify(...).
AssertJ - текучие (fluent) проверки: assertThat(x).isEqualTo(...).
Spring Test - контекст и срезы для интеграционных тестов; MockMvc и WebTestClient для проверки HTTP-слоя без реального сервера.
Testcontainers - поднимает настоящую БД или сервис в Docker на время теста.

Что важно знать про поведение тестов:
Подмена бинов в контексте. @MockBean/@SpyBean заменяют бин моком (в Boot 3.4+ на смену пришли @MockitoBean/@MockitoSpyBean). Полезно для @WebMvcTest, где сервис нужно замокать.
Кэширование контекста. Spring TestContext переиспользует контекст между тестами с одинаковой конфигурацией - он не пересоздаётся каждый раз. @DirtiesContext принудительно сбрасывает кэш.
Транзакция в тесте. @Transactional в тесте по умолчанию откатывает изменения после каждого метода.

Типичные ошибки:
H2 вместо реальной СУБД. Встроенная H2 не воспроизводит диалект и специфику прод-базы, и тест зелёный там, где прод падает. Для достоверности - Testcontainers.
@SpringBootTest на всё подряд. Полный контекст медленный; для узких проверок берите срезы.
Откатываемая транзакция маскирует LazyInitialization Exception и проблемы флаша, которые проявятся только на реальном коммите.
Мокать всё подряд. Моки уместны на границах (внешние сервисы, репозитории), а не для внутренней логики — иначе тест проверяет моки, а не поведение.


Логирование
Логи - основной способ узнать, что происходило в приложении в проде; вместе с метриками и трассировкой они составляют наблюдаемость (observability).
Фасад и реализация. Код пишется против фасада SLF4J, а конкретная реализация подключается отдельно. В Spring Boot по умолчанию это Logback (через spring-boot-starter-logging); альтернатива - Log4j2. Разделение позволяет менять реализацию, не трогая код.
Уровни. TRACE < DEBUG < INFO < WARN < ERROR; настраиваются по пакетам, поэтому можно поднять детализацию для своего кода и приглушить сторонние библиотеки.
Конфигурация. Простое - через application.yml (logging.level.*, формат, файл); сложное (аппендеры, ротация) - через logback-spring.xml.
MDC (Mapped Diagnostic Context). Контекст, привязанный к потоку (через ThreadLocal), куда кладут сквозные значения - например, correlation/trace id, - и они попадают в каждую строку лога запроса.
Трассировка. Micrometer Tracing (преемник Spring Cloud Sleuth) автоматически проставляет traceId/spanId в MDC, связывая логи одного запроса между сервисами.
Структурированное логирование. Вывод в JSON для агрегаторов (ELK, Loki); Spring Boot 3.4 добавил встроенную поддержку без сторонних библиотек.

Типичные ошибки
Конкатенация вместо плейсхолдеров. log.debug("x=" + heavy()) вычисляет аргумент всегда, даже если уровень выключен. Правильно - log.debug("x={}", heavy()): форматирование ленивое.
MDC не переходит в другой поток. Как SecurityContext и транзакции, он живёт в ThreadLocal и при @Async не наследуется - нужна явная пропагация.
Секреты и персональные данные в логах. Пароли, токены, PII логировать нельзя - это утечка и нарушение требований.
Двойное логирование. Поймать исключение, залогировать и пробросить дальше - оно запишется дважды. Логируйте либо там, где обрабатываете, либо на верхнем уровне.

Главная идея: пишите против SLF4J, управляйте детализацией по уровням и пакетам, а для диагностики распределённых запросов используйте MDC с trace id (Micrometer Tracing) и структурированный вывод. Ключевая дисциплина - параметризованные сообщения, отсутствие секретов в логах и понимание, что MDC, как и другие потоковые контексты, не переходит на другой поток.

11. Мониторинг и логирование.
Логирование - запись событий работы приложения (ошибки, предупреждения, информационные сообщения) с уровнями серьёзности от отладочных до критических, для последующего анализа.
Мониторинг - это слежение за состоянием уже работающего приложения в реальном времени: нагрузка, память, время отклика запросов. 
Логи отвечают на вопрос «что случилось и почему», мониторинг - «как сервис чувствует себя сейчас и как менялась картина». 
Логирование в Spring
SLF4J (Simple Logging Facade for Java) - это фасад, единый API для записи логов. В коде используют интерфейс Logger и фабрику LoggerFactory; приложение не зависит от конкретной библиотеки, которая реально пишет строки в файл или консоль. Если завтра понадобится Log4j2 вместо Logback, меняют зависимость и конфигурацию, а не каждый log.info(...) в сервисах.
Logback - реализация SLF4J, которая идёт по умолчанию в Spring Boot ( через spring-boot-starter-logging внутри spring-boot-starter). Именно Logback решает, куда и в каком виде попадёт сообщение: форматирует строку, выбирает appender, при необходимости ротирует файлы.
Внутри Logback работают три понятия:
Logger - точка входа с именем (обычно полное имя класса); решает, пропустить ли событие по уровню;
Appender - куда писать: консоль (ConsoleAppender), файл (RollingFileAppender с ротацией по размеру или дате);
Layout / Encoder - как оформить строку (шаблон с датой, уровнем, именем класса, %msg и т.д.).
private static final Logger log = LoggerFactory.getLogger(OrderService.class);
log.info("Order created: id={}", orderId);
log.error("Payment failed for order {}", orderId, exception);
Сообщения собирают с плейсхолдерами {}, а не конкатенацией строк: аргументы вычисляются и подставляются только если уровень включён. Последний аргумент может быть Throwable: тогда в лог попадёт stack trace.
Spring Boot поднимает Logback при старте и подмешивает настройки из application.yml / application.properties. Для нетривиальной схемы (разные форматы для prod и dev) кладут logback-spring.xml в src/main/resources. Обычный logback.xml загружается раньше и не видит часть Spring-конфигурации.
Уровни и конфигурация
Шкала уровней: TRACE < DEBUG < INFO < WARN < ERROR. Событие проходит, только если его уровень не ниже порога, заданного для logger’а. У Logback уровни наследуются по имени пакета: если для com.example.orders стоит DEBUG, а для root - INFO, пакет orders пишет подробнее, остальное приложение - только INFO и выше.
В логах фиксируют то, что поможет диагностике: идентификатор операции, исход внешнего вызова, неожиданные ветки. Не пишут секреты (пароли, токены, полные номера карт). Для высокого трафика избегают INFO на каждый мелкий шаг. В распределённых системах полезны структурированные логи (JSON) и корреляция запросов: один и тот же id проходит через несколько сервисов и связывает записи.
В Spring Web ошибка часто централизуется через @ControllerAdvice: там же уместно логировать исключение с контекстом запроса, не дублируя catch в каждом контроллере.
Мониторинг в Spring Boot
Spring Boot Actuator - модуль эксплуатационных эндпоинтов: готовность приложения, метрики, иногда сведения о окружении и конфигурации. Подключают стартером spring-boot-starter-actuator.
liveness - процесс «жив» (имеет смысл перезапустить, если нет);
readiness - готов принимать трафик (БД доступна, прогрев закончен);
health-агрегатор собирает индикаторы (диск, БД, очереди и т.д.).
В Boot 3 endpoints по умолчанию ограничены; нужные включают явно. Точные пути зависят от настроек; часто health доступен как /actuator/health. 
Не все endpoints стоит открывать наружу без защиты: env, подробный health с деталями могут раскрыть внутренности системы. Их либо не экспонируют публично, либо закрывают Spring Security / сетью.
Метрики и Micrometer
В Spring Boot метрики собирают через Micrometer. Kод и автоконфигурация Spring работают с единым API (MeterRegistry, Counter, Timer и др.), а куда передавать дальше решает подключённый registry - адаптер к конкретной системе хранения (Prometheus, InfluxDB, CloudWatch и т.д.)..
Spring Boot Actuator поднимает набор готовых метрик, наример, HTTP-запросы (число, latency, коды ответов), JVM (память, потоки, GC), иногда БД и пулы соединений. Кроме системных, в коде регистрируют бизнес-метрики - то, что важно продукту, а не только инфраструктуре: сколько заказов создано, сколько платежей упало, сколько сообщений обработано из очереди. 
Приложение через Micrometer накапливает метрики. Если на classpath есть micrometer-registry-prometheus, Actuator отдаёт их в формате Prometheus на endpoint вроде /actuator/prometheus. Prometheus периодически сам забирает (scrape) эти данные и хранит временные ряды. Grafana поверх них строит дашборды и алерты: «доля 5xx выше порога», «p95 latency выросла» и тд.
Трассировка
Пользовательский запрос может пройти через API-gateway, сервис заказов, платежи и склад, и непонятно, на каком звене ушла задержка или где впервые возникла ошибка. Distributed tracing (распределённая трассировка) как раз восстанавливает путь одного запроса по цепочке сервисов.
Понятие
Смысл
Trace
весь путь одного пользовательского (или системного) запроса через несколько сервисов
Span
один логический шаг внутри trace: обработка HTTP-запроса, вызов БД, обращение к другому сервису
traceId
общий идентификатор всего пути; одинаков во всех span’ах одного запроса
spanId
идентификатор конкретного шага; у дочернего span’а есть ссылка на родителя

Первый сервис, который принял запрос пользователя, создаёт traceId и свой первый шаг (корневой span). Когда он вызывает другой сервис, вместе с HTTP-запросом передаёт этот контекст в заголовках - соседний сервис видит тот же traceId и добавляет уже свой span. Благодаря этому все шаги одного запроса склеиваются в одну цепочку. В интерфейсе Jaeger, Zipkin или Grafana Tempo это выглядит как схема длительностей: сразу видно, какой вызов был самым долгим и где цепочка оборвалась ошибкой.
В Spring Boot 3 за трассировку отвечает Micrometer Tracing. Для приложения это привычный фасад (как Micrometer для метрик): код и автонастройки Spring работают с единым API, а под ним обычно лежит OpenTelemetry - общий стандарт, как именно описывать и передавать трейсы. Готовые трейсы отправляют во внешнюю систему просмотра - чаще всего в Jaeger или Zipkin. Исходящие и входящие HTTP-вызовы Spring часто помечает спанами сам; вручную спаны добавляют только для важных шагов, например «расчёт скидки» или «резерв на складе».
Польза раскрывается, когда трейсы связаны с логами. Если в каждую строку лога попадает тот же traceId (через MDC и шаблон Logback), разбор инцидента становится линейным: алерт в Grafana про рост задержки → в трейсе находят медленный шаг → по его traceId открывают логи и читают конкретную ошибку или медленный запрос к БД. Без общего идентификатора метрики, трейсы и логи приходится сопоставлять «на глаз» по времени. 

12. Обработка ошибок.
Когда в коде что-то идет не так (база прилегла, юзер ввел чушь, внешний API отвалился), Java выкидывает Exception. Если его не перехватить, Spring по умолчанию отдаст клиенту страшный стандартный JSON (Whitelabel Error Page) или, что еще хуже, вывалит наружу внутренности системы (стек-трейс).
Наша цель: Любое исключение должно превратиться в понятный, стандартизированный JSON-ответ с правильным HTTP-статусом.
В Spring обработка ошибок строится вокруг исключений (Exception). Если в каком-либо слое приложения возникает проблема, обычно не стоит пытаться обработать ее сразу. Вместо этого исключение поднимается выше по стеку вызовов, пока не достигнет слоя, который действительно знает, как на него реагировать.
Если база данных не смогла найти запись, репозиторий сообщает об этом через исключение. Сервис может либо преобразовать его в более понятную бизнес-ошибку, либо просто пробросить выше. Контроллер же вообще не должен заниматься разбором каждой ошибки вручную - это нарушает принцип разделения ответственности.
Именно поэтому в Spring существует глобальная обработка исключений.
Для этого используется @ControllerAdvice (или @RestControllerAdvice для REST API). Это специальный класс, который "слушает" исключения, возникшие в любом контроллере приложения. Если где-то было выброшено определенное исключение, Spring автоматически передаст управление соответствующему методу с аннотацией @ExceptionHandler.

Как это устроено под капотом
Когда в процессе работы вылетает исключение, DispatcherServlet не дает ему просто так разрушить поток. Он запускает цепочку поиска обработчиков:
-1. Поиск HandlerExceptionResolver: DispatcherServlet содержит список бинов, реализующих интерфейс HandlerExceptionResolver. Он по очереди опрашивает их: «Эй, ты умеешь обрабатывать это исключение?».
-2. Основные резолверы в стандартной поставке:
	– ExceptionHandlerExceptionResolver. Именно он ищет аннотации @ExceptionHandler внутри текущего контроллера или в глобальных @ControllerAdvice.
– ResponseStatusExceptionResolver: Ищет аннотацию @ResponseStatus на самом классе исключения или обрабатывает встроенные ResponseStatusException.
– DefaultHandlerExceptionResolver: Стандартный резолвер Spring, который переводит стандартные внутренние ошибки Spring в соответствующие HTTP-статусы (405 Method Not Allowed и т.д.).
Что происходит, если никто не обработал ошибку?
Если ни один резолвер не взял ошибку в работу, она пробрасывается на уровень контейнера сервлетов (например, Tomcat).
В Spring Boot по умолчанию настроен BasicErrorController (веб-интерфейс, маппится на путь /error). Tomcat делает внутренний перенаправленный запрос (forward) на /error, и этот контроллер возвращает тот самый стандартный Whitelabel JSON или HTML-страницу.

Ключевые аннотации и классы
@RestControllerAdvice: Объединяет @ControllerAdvice и @ResponseBody. Говорит Spring, что данный класс является глобальным перехватчиком, а возвращаемые им объекты должны автоматически сериализоваться в JSON/XML.
@ExceptionHandler: Вешается на методы внутри @RestControllerAdvice или обычного @Controller. Указывает, какие именно классы исключений этот метод должен перехватывать.
ResponseEntity<T>: Обертка над телом ответа, которая позволяет динамически управлять HTTP-статусом и заголовками. Вместо @ResponseStatus на методе лучше возвращать ResponseEntity<ErrorMessage>, так как это дает больше гибкости (например, можно вернуть разные статусы в зависимости от внутреннего состояния ошибки).
ProblemDetail (начиная со Spring 6 / Boot 3): Вместо создания своих кастомных ErrorMessage теперь рекомендуется использовать его, так как он задает единый отраслевой стандарт для описания ошибок в REST API.

13. Валидация данных.
Валидация - проверка, что данные соответствуют бизнес-правилам, до того как они попадут в основную логику или в БД. В экосистеме Java это стандартизировано спецификацией Bean Validation (JSR 380, сейчас - Jakarta Bean Validation): набор аннотаций и API для декларативного описания ограничений прямо на полях класса, вместо ручных if-проверок. Эталонная реализация - Hibernate Validator (не путать с Hibernate ORM, это разные проекты одной экосистемы).
Использование
Ограничения описываются аннотациями на полях DTO или сущности:
Аннотация
Проверяет
@NotNull
значение не null
@NotBlank
строка не null, не пустая и не только из пробелов
@NotEmpty
коллекция/строка не null и не пустая (пробелы допустимы)
@Size(min, max)
длина строки/коллекции в диапазоне
@Min / @Max
числовые границы
@Email
формат email
@Pattern(regexp = ...)
соответствие регулярному выражению
@Positive / @PastOrPresent и т.п.
более узкие числовые/временные ограничения


Чтобы проверка сработала на входе контроллера, аргумент помечают @Valid (стандарт Bean Validation) или @Validated (аннотация Spring, надмножество @Valid - умеет группы валидации):
@PostMapping("/users")
public ResponseEntity<UserDto> create(@Valid @RequestBody UserRequest request) {
    ...
}

Как это работает внутри
@Valid/@Validated - не магия, а точка расширения HandlerMethodArgumentResolver. При разборе аргумента @RequestBody резолвер видит аннотацию @Valid и после десериализации JSON вызывает Validator (реализация — Hibernate Validator) на полученном объекте. Каждое нарушенное ограничение превращается в FieldError, все ошибки собираются в BindingResult. Если контроллер не принимает BindingResult следующим параметром, Spring MVC сам выбрасывает MethodArgumentNotValidException  её и ловит @ControllerAdvice или стандартный DefaultHandlerException Resolver, формируя 400 Bad Request. В Spring 6 такой ответ по умолчанию оформляется как ProblemDetail (RFC 9457).
Важно различать, где применяется валидация:
@RequestBody + @Valid - проверка идёт через HandlerMethodArgumentResolver, ошибка → MethodArgumentNotValidException.
@Valid на пути/параметрах, @Validated на классе сервиса - это уже не MVC-резолвер, а AOP: MethodValidationInterceptor оборачивает бин прокси и проверяет аргументы/возврат метода. Ошибка здесь - не MethodArgumentNotValidException, а ConstraintViolation Exception, и её нужно обрабатывать отдельным @ExceptionHandler.
Валидация на уровне сущности (@Entity с аннотациями Bean Validation) срабатывает автоматически при flush через интеграцию Hibernate Validator с Hibernate ORM - это последний рубеж перед записью в БД, а не замена валидации на входе.

Свои правила и группы:
Кастомный валидатор. Своя аннотация (@interface) плюс класс, реализующий ConstraintValidator<Аннотация, Тип> с методом isValid. Нужен, когда встроенных ограничений недостаточно (например, проверка пароля на сложность) или когда правило зависит от нескольких полей сразу — тогда аннотацию вешают на класс, а не на поле, и валидатор получает весь объект.
Группы валидации. Один и тот же DTO может требовать разных правил в разных сценариях - например, id обязателен при обновлении, но не при создании. Для этого ограничения помечают интерфейсами-маркерами (@NotNull(groups = OnUpdate.class)), а на входе указывают нужную группу через @Validated(OnUpdate.class). Обычный @Valid группы не поддерживает - это одна из причин, почему @Validated используют на уровне класса и там, где нужна выборочная проверка.
Каскадная валидация. Вложенный объект проверяется, только если на поле, которое его содержит, стоит @Valid - без этой аннотации Bean Validation не спускается во вложенные объекты.

Типичные ошибки
@Valid вместо @Validated там, где нужны группы. @Valid не читает groups, поэтому попытка использовать группы с @Valid молча их игнорирует.
Забытый @Valid на вложенном поле. Без него ограничения вложенного DTO просто не проверяются - ошибок не будет, потому что валидатор туда не заходит.
Валидация только на входе в контроллер. Если тот же DTO/сущность может быть создан не через HTTP (например, из другого сервиса или батч-джобы), проверка на уровне контроллера не защищает эти пути — нужен Validator, вызванный явно, либо валидация на уровне сущности.
Смешивание источников ошибок. MethodArgumentNotValid Exception (из @RequestBody) и ConstraintViolationException (из method validation и валидации сущностей) - разные исключения с разной структурой; обработка только одного из них оставляет часть ошибок неотловленными и приводит к 500 вместо 400.
Дублирование правил между DTO и сущностью. Если ограничения не синхронизированы, проверка на входе может пропустить то, что упадёт уже при flush - с гораздо менее понятным сообщением об ошибке.


Главная идея: валидация описывается декларативно через Bean Validation, но фактически исполняется в разных точках - резолвером аргументов для @RequestBody, AOP-прокси для method validation, Hibernate при flush для сущностей - и каждая точка кидает своё исключение. Держите правила на границе входа (DTO), используйте @Validated и группы там, где нужна вариативность, и явно обрабатывайте оба вида исключений, а не только MethodArgumentNotValidException.

14. WebSockets.
WebSocket - протокол постоянного двустороннего соединения между клиентом и сервером поверх TCP. В отличие от обычного HTTP, где сервер может только отвечать на запрос клиента, здесь обе стороны могут в любой момент сами отправить сообщение друг другу без нового запроса. Для браузера адрес выглядит как ws://… или защищённый wss://… (аналог HTTPS).
Типичные сценарии: чаты, уведомления в реальном времени, совместное редактирование, дашборды с живыми метриками, мультиплеерные игры, статусы заказов/доставок. 

Основные характеристики WebSocket:
Двусторонняя связь между клиентом и сервером. 
Постоянное соединение между клиентом и сервером.
Меньше накладных расходов на установление соединений по сравнению с HTTP. 
Обмен данными в реальном времени - ключевая особенность WebSocket, позволяющая приложению мгновенно получать обновления и уведомления.
Структура WebSocket-соединения
Установка соединения начинается с TCP-соединение (для wss - сразу с TLS). По тому же каналу отправляет HTTP/1.1 GET на endpoint WebSocket.
Заголовки запроса клиента
Host - имя хоста сервера (обязательный заголовок HTTP/1.1).
Upgrade: websocket - явное указание желаемого протокола после перехода.
Connection: Upgrade - указание, что соединение должно быть переведено на другой протокол.
Sec-WebSocket-Key - случайная строка в Base64. По ней сервер строит Sec-WebSocket-Accept, чтобы клиент убедился, что ответ относится именно к WebSocket-handshake, а не является случайным 101.
Sec-WebSocket-Version: 13 - версия протокола WebSocket. 
Origin - источник страницы, с которой открывают сокет (браузер подставляет сам). Сервер использует его для проверки, что соединение инициировано с доверенного сайта.
Sec-WebSocket-Protocol (необязательный) - список желаемых подпротоколов, например v12.stomp. 
Sec-WebSocket-Extensions (необязательный) - расширения, например сжатие кадров (permessage-deflate).
Заголовки ответа сервера. При успешном handshake сервер отвечает кодом 101 Switching Protocols и набором заголовков.
Upgrade: websocket - подтверждение выбранного протокола.
Connection: Upgrade - подтверждение перехода.
Sec-WebSocket-Accept - вычисляется по правилу стандарта. К значению Sec-WebSocket-Key дописывают фиксированный GUID, применяют SHA-1 и кодируют результат в Base64. Клиент сверяет Accept с ожидаемым значением и только после этого считает канал установленным.
Sec-WebSocket-Protocol (если согласовывали) - тот подпротокол, который сервер принял.
Sec-WebSocket-Extensions (если согласовывали) - принятые расширения.
После handshake TCP-сокет перестаёт обслуживать HTTP. Обмен идёт фреймами с opcode и полезной нагрузкой. Код операции (opcode)  различает текст (0x1), бинарные данные (0x2), фрейм-продолжение (0x0), ping/pong (0x9/A) и close (0x8).
Закрытие соединения. Когда соединение больше не нужно, одна сторона (клиент или сервер) может отправить фрейм закрытия, который сигнализирует о завершении передачи данных. Сервер обязан освободить сессию, иначе накапливаются неактивные соединения.
Относительно polling выигрыш в том, что полные HTTP-заголовки ресурсозатратны в основном на этапе handshake, а дальнейший обмен легче. Обратная сторона - сервер удерживает открытые TCP-соединения. При большой аудитории это нагрузка на ресурсы процесса, ограничения прокси и задача горизонтального масштабирования. 
Ошибки при использовании WS
Открытый origin в проде. Разрешение allowedOrigins("*") позволяет открывать соединение к API со страницы любого сайта.
Отсутствие проверки на handshake. Без токена, cookie-сессии или HandshakeInterceptor канал доступен анонимно либо без контроля личности подключения.
Утечка сессий после отключения. Если в afterConnectionClosed сессия не удаляется из списка клиентов, на сервере накапливаются «мёртвые» соединения, растёт память и число неудачных попыток записи.
Несколько инстансов на simple broker. Встроенный брокер живёт в памяти одного процесса, поэтому сообщение доходит только до клиентов того же узла. Для кластера нужен внешний брокер или sticky sessions.
Неверная настройка прокси и балансировщика. Без поддержки HTTP Upgrade и долгих соединений handshake завершается ошибкой либо сессии обрываются по таймауту.
Слишком крупные полезные нагрузки. Передача через сокет больших JSON или файлов вместо короткого события и ссылки на REST-ресурс перегружает канал.
WebSocket без реальной необходимости. При редких событиях достаточно обычного запроса или SSE; постоянный канал только усложняет эксплуатацию.

Средства Spring
В Spring Boot подключают стартер spring-boot-starter-websocket. Далее выбирают уровень абстракции.
Низкий уровень - WebSocketHandler. На низком уровне Spring работает близко к протоколу. Нет топиков и автоматической маршрутизации сообщений. Есть эндпоинт, сессия и колбэки на события соединения. Подключают @EnableWebSocket, конфигурация реализует WebSocketConfigurer, в registerWebSocketHandlers регистрируют путь (например /ws/chat) и обработчик. Origin ограничивают через setAllowedOrigins / setAllowedOriginPatterns. При необходимости на тот же endpoint вешают HandshakeInterceptor - проверка токена или запись атрибутов в сессию ещё на этапе HTTP Upgrade.

Обработчик реализует интерфейс WebSocketHandler либо наследует готовые классы. TextWebSocketHandler удобен для текстового (часто JSON) обмена, BinaryWebSocketHandler - для бинарных данных. В жизненном цикле важны методы:
afterConnectionEstablished(WebSocketSession session) - соединение установлено, можно сохранить сессию в реестре клиентов;
handleTextMessage(WebSocketSession session, TextMessage message) - пришло текстовое сообщение;
handleBinaryMessage(...) - пришли бинарные данные (если нужен этот режим);
handleTransportError(WebSocketSession session, Throwable exception) - ошибка транспорта;
afterConnectionClosed(WebSocketSession session, CloseStatus status) - канал закрыт, сессию удаляют из реестра.
Ответ клиенту отправляют через WebSocketSession.sendMessage(...). У сессии есть идентификатор, URI, атрибуты handshake и флаг isOpen(). Рассылку нескольким клиентам на этом уровне делают вручную. Обычно держат потокобезопасную коллекцию активных WebSocketSession и при событии проходят по ней. Адресаты и формат полезной нагрузки - ответственность приложения.
Высокий уровень - STOMP. Если нужен не сырой канал, а подписки на топики и рассылка многим клиентам, в Spring обычно используют STOMP over WebSocket. Это простой messaging-протокол поверх WebSocket. WebSocket остаётся транспортом, STOMP задаёт, куда слать и на что подписываться. 
В этом случае применяется @EnableWebSocketMessageBroker, обработчики пишут через методы с @MessageMapping / @SendTo, исходящую рассылку из сервиса делают через SimpMessagingTemplate. 
Встроенный simple broker работает в памяти одного приложения. Если приложений несколько, нужен общий внешний брокер (RabbitMQ, ActiveMQ и т.п.).

15. Работа с очередями: интеграция с RabbitMQ, Kafka.
 Как удобно и надёжно работать с брокерами из Java-кода? Нативные клиенты (amqp-client для RabbitMQ, kafka-clients для Kafka) — низкоуровневые: разработчику приходится вручную управлять соединениями, каналами, потоками, сериализацией, повторными попытками. Именно эту проблему решают проекты Spring AMQP и Spring for Apache Kafka.
Общая философия Spring-интеграции
Spring применяет к брокерам тот же паттерн, что и к JDBC или REST: рутинную инфраструктуру берёт на себя фреймворк, а разработчик пишет только бизнес-логику. 
– Template для отправки. По аналогии с JdbcTemplate и RestTemplate существуют RabbitTemplate и KafkaTemplate - потокобезопасные объекты, инкапсулирующие соединение, сериализацию и протокольные детали. Без них каждая отправка требовала бы 15–20 строк boilerplate-кода с ручным управлением ресурсами и обработкой исключений.
– Listener-контейнер для приёма. Приём сообщений - это фоновая многопоточная работа: нужно держать соединение, опрашивать брокер, распределять сообщения по потокам, подтверждать обработку, восстанавливаться после сбоев. Spring прячет это в message listener container - инфраструктурный компонент, который сам управляет потоками и жизненным циклом, а разработчику оставляет метод с аннотацией @RabbitListener / @KafkaListener.
– Автоконфигурация Spring Boot. Достаточно добавить стартер (spring-boot-starter-amqp или spring-kafka) и несколько строк в application.yml - Boot сам создаст фабрики соединений, template'ы и фабрики контейнеров с разумными настройками по умолчанию.
-1. Интеграция с RabbitMQ: Spring AMQP
1.1 Соединения: CachingConnectionFactory
Первая проблема при работе с RabbitMQ - TCP-соединения и каналы (channels) дороги в создании. Открывать соединение на каждое сообщение - всё равно что для каждого письма заново заключать договор с почтой. Spring AMQP решает это через CachingConnectionFactory: она держит одно физическое соединение (или пул) и кеширует каналы, выдавая их коду по мере надобности и возвращая в кеш после использования.
1.2 Декларация топологии
Топологию кто-то должен создать на брокере. Делать это вручную через админку - путь к рассинхрону между кодом и инфраструктурой: приложение задеплоили на новый стенд, а очереди там нет.
Spring решает это декларативно: топология описывается как обычные бины, а компонент RabbitAdmin при первом открытии соединения автоматически объявляет их на брокере.
@Configuration
public class RabbitConfig {
   @Bean
   public Queue orderQueue() {
       return QueueBuilder.durable("order.created.queue")
               .withArgument("x-dead-letter-exchange", "dlx.exchange")
               .build();
   }
   @Bean
   public TopicExchange orderExchange() {
       return new TopicExchange("order.exchange");
   }
   @Bean
   public Binding binding(Queue orderQueue, TopicExchange orderExchange) {
       return BindingBuilder.bind(orderQueue)
               .to(orderExchange).with("order.created");
   }
}

Что здесь произошло: мы описали устойчивую (durable - переживающую рестарт брокера) очередь, topic-exchange и правило связывания «сообщения с ключом order.created класть в эту очередь». Spring при поднятии контекста находит все бины типов Queue, Exchange, Binding, и RabbitAdmin отправляет брокеру команды queue.declare, exchange.declare, queue.bind.
1.3. Отправка: RabbitTemplate и конвертация сообщений
Следующая проблема - сериализация. Брокер оперирует байтами, приложение - объектами. Без конвертера каждый вызов сопровождался бы ручным objectMapper.writeValueAsBytes(...) и сборкой AMQP-заголовков. Spring вводит абстракцию MessageConverter: по умолчанию используется Java-сериализация (плохо для межсервисного обмена - жёсткая привязка к классам), поэтому на практике почти всегда подключают Jackson2JsonMessageConverter.
1.4. Приём: @RabbitListener и listener container
Аннотация @RabbitListener над методом заставляет Spring создать для него SimpleMessageListenerContainer - компонент, который в фоновых потоках подписывается на очередь, получает сообщения, десериализует их тем же MessageConverter, вызывает ваш метод и подтверждает обработку.
@Component
public class OrderListener {
   @RabbitListener(queues = "order.created.queue", concurrency = "3-10")
   public void handle(OrderCreatedEvent event) {
       // бизнес-логика: создать доставку, отправить письмо и т.д.
       deliveryService.scheduleDelivery(event.orderId());
   }
}
Что происходит внутри. Контейнер открывает каналы, выполняет basic.consume и получает сообщения в push-режиме. Параметр concurrency = "3-10" означает: минимум 3 потребляющих потока, при росте нагрузки - до 10; так одной аннотацией решается задача горизонтального масштабирования обработки внутри инстанса. Ключевой механизм - подтверждения (acknowledgements). По умолчанию Spring использует режим AUTO: если метод завершился без исключения, контейнер отправляет брокеру basic.ack, и сообщение удаляется из очереди; если метод бросил исключение - отправляется basic.nack с requeue, и сообщение вернётся в очередь. 
1.5. Ошибки: retry и Dead Letter Queue
Если сообщение не проходит бизнес-валидацию (или по другим причинам возвращается обратно в брокер), режим requeue создаст бесконечный цикл - сообщение будет возвращаться и падать вечно, забивая логи и блокируя очередь. Решение двухступенчатое. 
Во-первых, Spring Retry: в конфигурации listener'а задаётся политика повторов (spring.rabbitmq.listener.simple.retry.* - например, 3 попытки с экспоненциальной задержкой), причём повторы происходят внутри контейнера, без возврата в брокер. 
Во-вторых, после исчерпания попыток сообщение отклоняется без requeue, и тут срабатывает x-dead-letter-exchange. Dead Letter Queue - «отдел невостребованных писем», где его можно исследовать, починить и переотправить вручную. Это стандартный промышленный паттерн: основной поток не блокируется, а ни одно сообщение не теряется бесследно.

2 Интеграция с Apache Kafka: Spring for Apache Kafka
Kafka концептуально иная, но с точки зрения Spring-разработчика API выглядит намеренно похоже, и это осознанное решение: снизить порог входа.
2.1. Отправка: KafkaTemplate
@Service
public class OrderEventProducer {
   private final KafkaTemplate<String, OrderCreatedEvent> kafkaTemplate;
   public OrderEventProducer(KafkaTemplate<String, OrderCreatedEvent> template) {
       this.kafkaTemplate = template;
   }


   public void send(OrderCreatedEvent event) {
       kafkaTemplate.send("order-events", event.orderId(), event)
           .whenComplete((result, ex) -> {
               if (ex != null) log.error("Send failed", ex);
           });
   }
}
KafkaTemplate обёртывает нативный KafkaProducer, который создаётся ProducerFactory из свойств spring.kafka.producer.*. Сериализация здесь настраивается иначе, чем в RabbitMQ, - через сериализаторы ключа и значения (JsonSerializer для value). Второй аргумент - ключ сообщения: Kafka хеширует его и по хешу выбирает партицию. Почему это критично: Kafka гарантирует порядок только внутри партиции, поэтому, передавая orderId как ключ, мы гарантируем, что все события одного заказа попадут в одну партицию и будут обработаны строго по порядку. Метод возвращает CompletableFuture - отправка асинхронная: сообщения сначала копятся в буфере producer'а и отправляются батчами, а колбэк сработает, когда брокер подтвердит запись. Уровень надёжности регулируется свойством acks.
2.2. Приём: @KafkaListener, consumer group и партиции
@Component
public class OrderEventListener {


   @KafkaListener(topics = "order-events",
                  groupId = "delivery-service",
                  concurrency = "3")
   public void onOrderCreated(OrderCreatedEvent event) {
       deliveryService.scheduleDelivery(event.orderId());
   }
}
Здесь ключевое понятие - consumer group (groupId). Проблема, которую она решает: как масштабировать чтение и при этом не обработать одно сообщение дважды разными инстансами сервиса? Kafka распределяет партиции топика между членами группы: каждая партиция читается ровно одним consumer'ом группы. Аналогия - окна в отделении почты: посетители (партиции) закреплены за конкретными окнами (потребителями), и если оператор ушёл, его посетителей перераспределяют между оставшимися (это называется rebalance). Разные группы независимы: delivery-service и analytics-service с разными groupId оба получат все сообщения - так реализуется pub/sub.
Внутри Spring создаёт ConcurrentMessageListenerContainer: параметр concurrency = "3" порождает три потока, каждый со своим KafkaConsumer, и Kafka раздаёт им партиции. Отсюда важное следствие для практики: бессмысленно ставить concurrency больше числа партиций - лишние потоки останутся без работы. 
Вместо ack'ов здесь работает коммит offset'ов: контейнер периодически (режим по умолчанию BATCH) сообщает Kafka, до какой позиции группа дочитала. Если инстанс упал до коммита - после rebalance другой инстанс перечитает сообщения с последнего закоммиченного offset'а.
2.3. Ошибки: DefaultErrorHandler и Dead Letter Topic
У Kafka нет встроенного DLQ-механизма, как у RabbitMQ, поэтому Spring реализует его на своей стороне. По умолчанию контейнер использует DefaultErrorHandler: при исключении он делает несколько повторов (по умолчанию с небольшим интервалом), а затем может передать сообщение в DeadLetterPublishingRecoverer, который публикует его в Dead Letter Topic.

16. Контейнеризация: Docker и Spring Boot.
 Контейнеризация упаковывает Spring Boot приложение вместе с JVM и всем окружением в образ, который одинаково запускается и локально, и в оркестраторе. Специфика именно Spring Boot - в том, что стандартный «толстый» jar (fat jar) плохо ложится на слоистую модель Docker-образов, и экосистема выработала свои решения этой проблемы.
 Базовый Dockerfile:
 
 FROM eclipse-temurin:21-jre-alpine
 WORKDIR /app
 COPY target/app.jar app.jar
 ENTRYPOINT ["java", "-jar", "app.jar"]

 Он рабочий, но неэффективный: fat jar содержит и код приложения, и все зависимости одним слоем. При каждой пересборке (даже если поменялась одна строчка кода) Docker обязан заново закачивать в реестр весь слой целиком - зависимости, которые не менялись, тоже.

 Layered jar: почему и как
 Начиная со Spring Boot 2.3, jar можно собирать в слоистом (layered) формате: содержимое делится на несколько слоёв по частоте изменения - dependencies (обычные библиотеки, меняются редко), spring-boot-loader (сам загрузчик, почти никогда), snapshot-dependencies (SNAPSHOT-зависимости), application (код приложения, меняется каждую сборку).
 Слои извлекаются инструментом spring-boot-jarmode-layertools, встроенным в исполняемый jar, и раскладываются по отдельным COPY-слоям Docker в порядке от самого стабильного к самому изменчивому - это классический multi-stage Dockerfile:
FROM eclipse-temurin:21-jdk-alpine AS builder
WORKDIR /app
COPY target/app.jar app.jar
RUN java -Djarmode=layertools -jar app.jar extract

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=builder /app/dependencies/ ./
COPY --from=builder /app/spring-boot-loader/ ./
COPY --from=builder /app/snapshot-dependencies/ ./
COPY --from=builder /app/application/ ./
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

 Смысл - в кэшировании слоёв Docker: если код приложения поменялся, а зависимости нет, пересобирается и перезаливается только последний, самый лёгкий слой application; слой dependencies (обычно самый тяжёлый) переиспользуется из кэша. Это ускоряет и пересборку, и деплой в реестр.

  Cloud Native Buildpacks
 Альтернатива ручному Dockerfile - Spring Boot умеет собирать OCI-образ напрямую из исходников через Cloud Native Buildpacks (Paketo), без Dockerfile вообще:

  ./mvnw spring-boot:build-image
  # или
  ./gradlew bootBuildImage

Buildpacks сами определяют рантайм, версию JDK, кладут слои в правильном порядке и умеют собирать native image через GraalVM-buildpack - тогда вместо JVM в образе оказывается нативный исполняемый файл. Плюс - не нужно поддерживать Dockerfile руками и заботиться о best practices вручную; минус - меньше контроля над содержимым образа и более тяжёлый инструмент сборки.

  JVM в контейнере: контроль над ресурсами
  JVM исторически определяла доступную память и число CPU по хосту, а не по cgroup-лимитам контейнера - в контейнере с лимитом 512 МБ она могла решить, что доступно намного больше, и получить OOMKilled. Начиная с JDK 10+ (и особенно стабильно - с JDK 11+), JVM «осведомлена о контейнере» (container-aware): по умолчанию учитывает cgroup-лимиты.
  Практические флаги:
-XX:MaxRAMPercentage - доля лимита контейнера, отдаваемая под heap (лучше фиксированного -Xmx, потому что подстраивается под лимит контейнера, а не зашита в образ).
-XX:ActiveProcessorCount - если оркестратор режет CPU через cgroup quota, а не через nproc, JVM может неверно определить число доступных потоков для пулов (например, ForkJoinPool) - это можно задать явно.

 Типичные ошибки
Fat jar одним слоем в проде. Работает, но каждая пересборка гоняет по сети мегабайты неизменившихся зависимостей - используйте layered jar.
Запуск от root внутри контейнера. Базовые образы часто по умолчанию root; для прод-образа стоит явно переключаться на непривилегированного пользователя (USER в Dockerfile или готовый non-root базовый образ).
Фиксированный -Xmx без учёта лимита контейнера. Если лимит контейнера уменьшили, а -Xmx остался прежним - либо потрачена память впустую, либо OOMKilled; отсюда предпочтение MaxRAMPercentage.
Смешивание JDK и JRE. Финальный слой рантайма должен быть на JRE (или на образе с JDK, только если он реально нужен рантайму) - тащить полный JDK в продакшен-образ бессмысленно раздувает его размер.

Главная идея: контейнеризация Spring Boot - это не просто «положить jar в Docker», а работа с тем, как JVM ведёт себя в ограниченном по ресурсам контейнере и как слои образа кэшируются. Используйте layered jar или buildpacks вместо fat jar одним слоем и отдавайте JVM управление ресурсами через MaxRAMPercentage, а не через захардкоженный -Xmx.

17. Структура HTML-документа.
HTML - это стандартизированный язык гипертекстовой разметки, используемый для создания веб-страниц в интернете. Он представляет собой набор элементов, которые служат скелетом любой веб-страницы и задают ее базовую структуру. Сам термин «гипертекстовый» означает, что текст содержит в себе ссылки на другие документы или части одного документа. 
HTML позволяет организовать информацию в логические блоки и обеспечивает семантическую разметку содержимого. Кроме того, правильная HTML-структура помогает поисковым системам лучше понимать содержимое страницы и упрощает индексацию сайта, что в конечном итоге влияет на позиции сайта в поисковой выдаче.
Минимальный HTML5-документ:
<!DOCTYPE html>
<html lang="ru">
<head>
   <meta charset="UTF-8">
   <meta name="viewport" content="width=device-width, initial-scale=1.0">
   <title>Заголовок вкладки</title>
   <link rel="stylesheet" href="styles.css">
</head>
<body>
   <!-- видимое содержимое страницы -->
</body>
</html>


<!DOCTYPE html> - элемент всегда стоит первым в документе и указывает браузеру, что документ написан на HTML5. Он не чувствителен к регистру, но принято писать его заглавными буквами для лучшей читаемости.
<html> - корневой элемент, который включает весь контент на странице. Все остальные теги должны находиться внутри этого элемента.
<head> - раздел с метаданными, которые не видны обычному пользователю при просмотре сайта. 
<title> задаёт текст вкладки браузера и часто используется в выдаче поиска. <meta charset="…"> указывает кодировку (для современных страниц обычно UTF-8). viewport-meta нужен для корректного масштаба на мобильных устройствах. Через <link> подключают стили, favicon и другие связанные ресурсы. 
Скрипты могут подключаться и в head, и в конце body - выбор влияет на порядок загрузки и скорость отрисовки, но это уже вопрос оптимизации, а не самой структуры.
<body> - тело документа - весь контент, который пользователь видит на сайте.
body содержит видимую разметку. В HTML5 её принято строить семантически. Теги выбирают по смыслу блока (шапка, навигация, основной контент, подвал), а не только как универсальные коробки для CSS. Универсальный контейнер без семантики - <div> - остаётся инструментом вёрстки, но не заменяет смысловые секции там, где смысл важен.

18. Разметка текста. Ссылки и изображения.
HTML (HyperText Markup Language) - это язык разметки, который описывает структуру веб-страницы. Его задача - не определять внешний вид страницы, а объяснить браузеру, что именно находится на странице: заголовок, абзац, ссылка, изображение, список и т.д. Оформлением занимается CSS, а логикой - JavaScript.
Разметка текста
При создании веб-страницы важно использовать семантические элементы, которые отражают смысл содержимого. Это делает код более понятным для разработчиков, поисковых систем и вспомогательных технологий
Основные элементы разметки текста:
<h1>–<h6> - заголовки разных уровней;
<p> - абзац;
<strong> - важный текст (обычно отображается жирным);
<em> - логическое выделение текста (обычно курсив);
<ul> и <ol> - маркированные и нумерованные списки;
<li> - элемент списка.

Ссылки
Ссылки создаются с помощью тега <a> (anchor). Именно благодаря ссылкам HTML получил название HyperText - страницы могут быть связаны между собой.
<a href="https://example.com" target="_blank" rel="noopener">Посетить сайт</a>
Ссылки бывают:
– внутренние - переход между страницами одного сайта;
– внешние - переход на другой сайт;
– якорные - переход к определенному месту внутри страницы.
Основным атрибутом является href, который указывает адрес перехода.
Разберем атрибуты:
href (hypertext reference): Адрес, куда мы отправляем пользователя. Может быть абсолютным (https://google.com), относительным (/about), или якорем внутри страницы (#contacts). Может запускать действия: mailto:hr@company.com (открыть почту) или tel:+79991112233 (позвонить).
target="_blank": Открывает ссылку в новой вкладке.
rel="noopener": Критически важно для безопасности! Если вы используете target="_blank", обязательно добавляйте rel="noopener" (или noopener noreferrer). Без этого открытая страница получает доступ к вашему объекту window.opener через JavaScript и может незаметно подменить адрес вашей страницы на фишинговый сайт.

Изображения
Для вставки изображений используется тег <img>. В отличие от большинства HTML-тегов, он не имеет закрывающей части.
<img src="images/logo.webp" alt="Логотип компании в векторе" loading="lazy">
Основные атрибуты изображения:
src - путь к файлу изображения;
alt - альтернативное текстовое описание;
width и height - размеры изображения.
Особое значение имеет атрибут alt. Он используется:
– если изображение не удалось загрузить;
– для людей, использующих программы экранного доступа;
– поисковыми системами при индексации страницы.
Поэтому alt должен описывать содержимое изображения, а не повторять имя файла.

19. Основы CSS.
CSS (Cascading Style Sheets) - язык описания того, как размечённый HTML-документ должен выглядеть: цвета, размеры, расположение элементов. Ключевое слово в названии - «каскадные»: правила не применяются изолированно, а объединяются по определённому алгоритму, когда к одному элементу подходит несколько правил сразу. Это и есть главная концептуальная сложность CSS - не отдельные свойства, а то, как они взаимодействуют.
Синтаксис и селекторы
Правило CSS - это селектор (что стилизуем) плюс блок объявлений (что применяем):
.card {
  color: #333;
  font-size: 16px;
}

Каскад и специфичность - как решается конфликт правил:
Когда несколько правил применимы к одному элементу, побеждает не «последнее написанное» и не «самое короткое», а результат конкретного алгоритма - каскада, который сравнивает правила по нескольким критериям по очереди:
Происхождение и важность. Стили автора страницы обычно перебивают стили браузера по умолчанию; !important переворачивает порядок и получает наивысший приоритет (кроме анимаций) - поэтому его использование затрудняет дальнейшую поддержку каскада и считается плохой практикой в обычном коде.
Специфичность (specificity). Считается как тройка (id, классы/атрибуты/псевдоклассы, теги/псевдоэлементы). У ID-селектора вес больше, чем у любого числа классов; у класса - больше, чем у любого числа селекторов по тегу. Специфичность не «складывается» в одно число - сравнение идёт по разрядам слева направо, как в позиционной системе счисления.
Порядок появления в коде. Если специфичность равна, побеждает правило, объявленное позже.

Отдельно от специфичности работает наследование: часть свойств (цвет текста, шрифт) по умолчанию передаётся от родителя к потомку, если явно не переопределена, а часть (border, padding, background) - нет.

Модели компоновки: как элементы занимают место
CSS предлагает несколько алгоритмов раскладки, и элемент попадает в тот или иной в зависимости от display и контекста:
Обычный поток (normal flow) - поведение по умолчанию: блочные элементы (div, p) выстраиваются друг под другом на всю ширину контейнера, строчные (span, a) - в строку, перетекая на следующую.
position - выводит элемент из обычного потока или переопределяет точку отсчёта. relative смещает элемент относительно его исходного места, не забирая место у соседей. absolute полностью убирает элемент из потока и позиционирует его относительно ближайшего предка с position не static (это и называется containing block) - типичная ошибка новичков: absolute без позиционированного родителя привязывается к границам всего документа. fixed привязывает элемент к области просмотра. sticky ведёт себя как relative, пока элемент в зоне видимости, и «прилипает» как fixed при прокрутке за заданную границу.
Flexbox (display: flex) - одномерная раскладка: элементы выстраиваются вдоль одной оси (строка или столбец) с гибким распределением свободного места (justify-content, align-items, flex-grow/flex-shrink). Хорошо подходит для расположения элементов в ряд или столбец с равномерным распределением.
Grid (display: grid) - двумерная раскладка: одновременно задаются и строки, и столбцы, элементы размещаются в ячейках сетки. Подходит для целостной компоновки страницы, а не отдельного ряда элементов.

Единицы измерения
Абсолютные - px: не масштабируются от контекста.
Относительные к шрифту - em (относительно размера шрифта родителя, поэтому вложенность может давать неожиданное накопление), rem (относительно размера шрифта корневого элемента html - предсказуемее em именно поэтому).
Относительные к области просмотра - %, vw/vh (проценты от ширины/высоты окна просмотра).

Типичные ошибки
Борьба со специфичностью через !important вместо понимания каскада - быстро приводит к состоянию, где перебить стиль можно только ещё бо́льшим !important.
margin вместо padding, когда нужно увеличить кликабельную область - margin не входит в блок элемента и не расширяет область его собственного фона/границы.
Схлопывание вертикальных отступов (margin collapse) - соседние вертикальные margin двух блочных элементов в обычном потоке не складываются, а схлопываются в больший из двух; это специфика именно вертикальных внешних отступов в normal flow.
position: absolute без позиционированного родителя - элемент привязывается не к ближайшему контейнеру, а к документу целиком, и «уезжает» при любом изменении контента выше.
Смешение процентов и разных единиц без понимания контекста - % для width считается от родителя, а % для margin/padding - тоже от ширины родителя, даже если сам margin/padding вертикальный, что часто удивляет.

Главная идея: CSS - это не список изолированных свойств, а система с двумя уровнями правил: каскад решает, какое из конкурирующих объявлений победит (происхождение → специфичность → порядок), а модель компоновки (flow, position, flex, grid) решает, как побеждающие правила превращаются в реальное расположение на странице. Путаница в CSS почти всегда происходит на стыке этих двух систем - специфичность объясняет, «чьё правило» применилось, а модель компоновки - «почему элемент оказался именно там».

20. Таблицы и формы.
Таблица строится из контейнера, строк внутри него, обычных ячеек и ячеек заголовка (выделяются жирным и по центру автоматически); можно отдельно выделить шапку, тело и подвал таблицы для смысловой структуры. 
Задаются тегом <table>. Строки создаются с помощью <tr>, ячейки с данными — <td>, а заголовки — <th>
Форма — контейнер с адресом отправки и методом (получить/отправить), внутри — поля ввода разных типов, подписи к полям (связываются с полем по идентификатору, тогда клик по подписи ставит курсор в поле) и кнопка отправки.
Определяются тегом <form>. Основной элемент ввода — <input>, тип которого зависит от задачи (text, password, checkbox, submit). Для ввода текста в несколько строк используют <textarea>.
<form action="/submit" method="POST">
  <label>Имя:
    <input type="text" name="username">
  </label>
  <button type="submit">Отправить</button>
</form>

21. Селекторы и наследование.
Селекторы - это паттерны, которые указывают браузеру, к каким HTML-элементам применить правила стилей. Их можно разделить на несколько ключевых групп.
Базовые селекторы:
Универсальный селектор (*): Выбирает вообще все элементы на странице. Обычно используется для сброса базовых отступов:
* {
 box-sizing: border-box;
 margin: 0;
}
Селектор типа (тега): Выбирает элементы по имени HTML-тега (например, p, h1, div). Полезен для задания глобальных правил.
Селектор класса (.className): Стилизует все элементы с этим классом.
Селектор идентификатора (#idName): Начинается с решетки. Нацелен на один уникальный элемент на странице.

Комбинаторы: Связи между элементами
Часто нужно выбрать элемент не просто так, а в зависимости от того, где он находится в структуре HTML.
Название комбинатора
Пример
Что выберет?
Дочерний (parent > child)
.card > p
Только те <p>, которые лежат непосредственно внутри .card (первый уровень вложенности).
Потомственный (ancestor descendant)
.card p
Вообще все <p> внутри .card, независимо от глубины их вложенности.
Соседний (prev + next)
h2 + p
Элемент <p>, который идет в HTML-коде сразу же после h2 (на одном уровне).
Родственный (prev ~ siblings)
h2 ~ p
Все <p>, которые идут после h2 на этом же уровне вложенности.


Псевдоклассы и псевдоэлементы
Это мощный инструмент для динамики и микро-взаимодействий без JavaScript.
– Псевдоклассы (одно двоеточие :): Описывают особое состояние элемента.
:hover - когда на элемент наведен курсор.
:focus - когда элемент активен (например, инпут при вводе текста).
:nth-child(n) - позволяет выбирать элементы по их порядковому номеру (например, каждую четную строку в таблице: :nth-child(even)).

– Псевдоэлементы (два двоеточия ::): Позволяют стилизовать виртуальные части элемента или создавать их "на лету".
::before и ::after - создают виртуальный элемент внутри целевого элемента. Обязательно требуют наличия свойства content: "". Идеально для декоративных иконок или кастомных маркеров.
::placeholder - стилизует подсказку внутри инпута.

Наследование: Что переходит по наследству?
Наследование (Inheritance) - это механизм, при котором некоторые CSS-свойства автоматически передаются от родительских элементов к их потомкам.
Что наследуется, а что нет?
Интуитивно это понять очень просто: наследуется всё, что связано с текстом и его форматированием, потому что вы хотите, чтобы весь ваш текст в блоке выглядел единообразно.
Наследуются: color, font-family, font-size, line-height, text-align, list-style.
НЕ наследуются: Всё, что связано с геометрией, позиционированием и границами (Box Model). Было бы катастрофой, если бы вы задали для div рамку border: 1px solid red и внутренний отступ padding: 20px, а они применились бы ко всем ссылкам, кнопкам и текстам внутри него.
(Не наследуются: border, margin, padding, width, height, background, position, display).
Как этим управлять?
Вы можете принудительно изменить поведение по умолчанию с помощью специальных значений:
– inherit: Заставляет элемент взять значение этого свойства у своего родителя (даже если оно обычно не наследуется).
– initial: Сбрасывает свойство до дефолтного значения, прописанного в спецификации браузера.
– unset: Работает как "умный сброс": если свойство наследуемое, оно ведет себя как inherit, а если нет - как initial.

Специфичность (Вес селекторов): Кто кого поборет?
Специфичность можно представить в виде четырехзначного числа (0, 0, 0, 0):
Inline-стили (написанные прямо в HTML через атрибут style="") - весят 1000.
ID селекторы (#id) - весят 100.
Классы, атрибуты и псевдоклассы (.class, [type="text"], :hover) - весят 10.
Теги и псевдоэлементы (p, div, ::before) - весят 1.
Если вы допишете к свойству !important (например, color: red !important;), это свойство перебьет любые правила специфичности.

22. Сетки и гриды.
Слово «сетка» в вебе означает две разные вещи, и их стоит сразу развести. Дизайн-сетка (grid system) - это концепция компоновки страницы на колонки (классически — 12), которую годами реализовывали через float или flex в фреймворках вроде Bootstrap. CSS Grid Layout - нативный модуль CSS, появившийся заметно позже и решающий ту же задачу на уровне самого языка, без обёрточных <div> и хаков. Ниже - именно про CSS Grid, поскольку он и вытеснил большинство самодельных сеток.

Базовое использование
Грид включается на контейнере и описывается через явные строки и столбцы:
.grid {
  display: grid;
  grid-template-columns: 200px 1fr 1fr;
  grid-template-rows: auto 1fr;
  gap: 16px;
}

grid-template-columns / grid-template-rows — задают трек-структуру (число и размер строк/столбцов).
fr (fraction unit) - доля свободного пространства после вычитания фиксированных треков и отступов; 1fr 2fr делит оставшееся место в отношении 1:2, а не всей ширины контейнера.
gap (бывший grid-gap) - расстояние между треками, без необходимости в margin-хаках, которые давали лишний отступ по краям.
repeat() - сокращение для повторяющихся треков: repeat(3, 1fr) эквивалентно 1fr 1fr 1fr.
minmax() - задаёт диапазон размера трека: minmax(200px, 1fr) не даст колонке сжаться меньше 200px.

Элементы позиционируются либо автоматически (по порядку в разметке), либо явно по номерам линий сетки:
.item {
    grid-column: 1 / 3;   /* от линии 1 до линии 3 — на два трека */
    grid-row: 2;
  }

Явный и неявный грид
	Здесь начинается то, что реально отличает уверенное владение CSS Grid от поверхностного. Треки, описанные в grid-template-columns/ grid-template-rows, образуют явный (explicit) грид. Если элементов больше, чем ячеек, или элемент явно спозиционирован за пределы заданной структуры, браузер сам достраивает недостающие строки/столбцы - это неявный (implicit) грид, и его размер по умолчанию - auto (подстраивается под содержимое), если не задан через grid-auto-rows/grid-auto-columns.
Алгоритм автоматического размещения (auto-placement) - то, как элементы без явных координат заполняют сетку: по умолчанию построчно слева направо (grid-auto-flow: row), при column - по столбцам сверху вниз. Значение dense меняет алгоритм так, чтобы плотнее заполнять пропуски более мелкими последующими элементами, даже нарушая порядок разметки - из-за чего визуальный порядок может разойтись с порядком в DOM, что важно для доступности (screen reader читает по DOM-порядку).

Именованные области
grid-template-areas описывает раскладку буквально как ASCII-картинку, что делает структуру страницы читаемой прямо в CSS:
.layout {
  display: grid;
  grid-template-areas:
    "header header"
    "sidebar content"
    "footer footer";
  grid-template-columns: 200px 1fr;
}
.header  { grid-area: header; }
.sidebar { grid-area: sidebar; }
.content { grid-area: content; }
.footer  { grid-area: footer; }

Каждая строка в кавычках - это ряд сетки, а повторяющееся имя объединяет ячейки в одну область. Пустая ячейка обозначается точкой (.).

Выравнивание: два независимых набора свойств
Grid (как и Flexbox) разделяет выравнивание по двум осям через отдельные свойства, и это частый источник путаницы:

	Subgrid
По умолчанию вложенный грид не видит трек-структуру родителя - у него собственная независимая сетка, из-за чего колонки вложенных гридов не выравниваются между собой. grid-template-columns: subgrid (и аналогично для строк) заставляет вложенный элемент наследовать линии сетки родителя вместо создания своих - это решает задачу выравнивания карточек разной вложенности по общим колонкам без магических чисел.

	Практическое правило: если раскладываете элементы в одном направлении и им важно гибко делить пространство - Flexbox; если нужно одновременно контролировать и строки, и столбцы - Grid. Они не взаимоисключающие: Grid для общей структуры страницы, Flexbox - для компоновки содержимого внутри отдельных областей грида - обычный рабочий паттерн.

	Типичные ошибки
Путать fr с процентами. fr делит оставшееся пространство после фиксированных треков, а не всю ширину контейнера - 200px 1fr 1fr даёт две равные колонки из оставшегося места, а не по 50% ширины контейнера.
Забывать про неявный грид. Если элементов больше, чем ячеек в explicit-гриде, лишние не теряются, а уезжают в implicit-треки с размером auto - из-за этого раскладка «внезапно» меняется при добавлении контента, если не задан grid-auto-rows.
justify-* и align-* наоборот. Их легко перепутать местами, особенно переключаясь между Flexbox (где направление осей меняется при flex-direction: column) и Grid (где оси фиксированы: строчная и блочная).
dense без учёта DOM-порядка. Плотная упаковка визуально выглядит аккуратно, но рвёт связь между порядком в разметке и порядком на экране - проблема для навигации с клавиатуры и скринридеров.
Grid там, где хватило бы Flexbox, и наоборот. Одномерный ряд карточек через Grid с одной строкой - избыточно; попытка выразить сложную двумерную раскладку через вложенные flex-контейнеры - обычно более хрупкое решение, чем один Grid с grid-template-areas.

Главная идея: CSS Grid - двумерная система: сначала описывается структура (явные треки через grid-template-columns/rows или areas), а незаполненное браузер достраивает по алгоритму auto-placement в неявный грид. Выбор между Grid и Flexbox - это выбор между «нужна структура по двум осям» и «нужно гибкое поведение вдоль одной», а не вопрос того, какой инструмент современнее.

23. JavaScript. Коллекции. Свойства. Операторы.
Основные коллекции: 
массив (упорядоченный список), 
объект (набор пар «ключ-значение»), 
Map (то же самое, но ключом может быть что угодно, не только строка, и порядок вставки сохраняется), 
Set (набор уникальных значений без повторов). 
Свойства объекта читаются через точку либо через квадратные скобки (нужны, если имя свойства заранее не известно). Из операторов важно различать сравнение с приведением типов и без него — второе (строгое) в грамотном коде используют почти всегда, чтобы не получать неожиданных результатов при сравнении разных типов.
Подвох: проверка типа для значения null возвращает «объект» — это давняя ошибка языка, сохранённая ради совместимости со старым кодом, а не логичное поведение.


24. Динамические стили.
Динамические стили - это изменение внешнего вида веб-страницы во время ее работы без перезагрузки страницы. В отличие от обычного CSS, который применяется один раз при загрузке документа, динамические стили позволяют изменять оформление в ответ на действия пользователя или изменения состояния приложения.
Основным инструментом для управления динамическими стилями является JavaScript, который взаимодействует с DOM (Document Object Model) и может изменять свойства HTML-элементов.
Существует несколько способов изменения стилей:
– изменение отдельных CSS-свойств через объект element.style;
– добавление или удаление CSS-классов с помощью classList;
– изменение атрибута class;
– изменение CSS-переменных (Custom Properties).
На практике изменение классов считается предпочтительным способом, поскольку JavaScript отвечает только за логику, а все оформление остается в CSS. Это делает код более читаемым и удобным для сопровождения.
Динамические стили используются во многих элементах современных веб-приложений:
– переключение светлой и темной темы;
– открытие и закрытие меню;
– отображение модальных окон;
– подсветка выбранных элементов;
– отображение ошибок в формах;
– анимации при наведении или клике;
– адаптация интерфейса после получения данных с сервера.

1 Подход №1 (Best Practice): Управление классами
Это самый чистый и производительный способ. Суть в том, что все стили для разных состояний элемента вы заранее описываете в CSS-файле, а с помощью JavaScript просто добавляете или удаляете нужные классы.
CSS (определяем состояния):
/* Базовый стиль уведомления */
.toast {
 padding: 15px;
 background-color: #f0f0f0;
 transition: opacity 0.3s ease;
 opacity: 0;
}
/* Состояние "активно" */
.toast.is-active {
 opacity: 1;
}
/* Состояние "ошибка" */
.toast.is-error {
 background-color: #ffcccc;
 border: 1px solid #ff0000;
}
JavaScript переключает состояния:
const toast = document.querySelector('.toast');
function showErrorMessage() {
 // Добавляем класс активности и класс ошибки
 toast.classList.add('is-active', 'is-error');
}
function hideMessage() {
 // Удаляем класс активности
 toast.classList.remove('is-active');
}
Инструментарий JS (element.classList):
classList.add('class') - добавить класс.
classList.remove('class') - удалить класс.
classList.toggle('class') - если класса нет, добавить его; если есть - удалить.
classList.contains('class') - проверить, есть ли класс у элемента (возвращает true/false).

2. Подход №2: Прямое изменение инлайновых стилей
Иногда нам действительно нужно задать стиль, который мы не можем знать заранее (в CSS-файле). Например: координаты курсора мыши для кастомного тултипа, процент загрузки файла в прогресс-баре или динамическая высота раскрывающегося блока.
Для этого в JS используется свойство element.style.
JavaScript:
const progressBar = document.querySelector('.progress-fill');
const tooltip = document.querySelector('.tooltip');
// Пример 1: Изменение ширины прогресс-бара на основе динамических данных
function updateProgress(percent) {
 progressBar.style.width = `${percent}%`;
}
// Пример 2: Позиционирование элемента за курсором мыши
window.addEventListener('mousemove', (event) => {
 tooltip.style.left = event.clientX + 'px';
 tooltip.style.top = event.clientY + 'px';
});

3 Подход №3: JS + CSS Custom Properties
Это современный и невероятно мощный гибридный подход. Вместо того чтобы менять десятки инлайновых стилей у кучи элементов, мы можем с помощью JS изменить значение одной CSS-переменной на уровне корня документа или конкретного родителя. Все дочерние элементы, использующие эту переменную, обновятся автоматически.
CSS:
:root {
 /* Объявляем переменную темы */
 --theme-color: #3498db;
}
.button {
 background-color: var(--theme-color);
}
.sidebar {
 border-left: 3px solid var(--theme-color);
}
JavaScript:
// Меняем значение переменной во всем документе
function changeThemeColor(newColor) {
 document.documentElement.style.setProperty('--theme-color', newColor);
}
// Вызываем функцию, например, при клике на палитру цветов
changeThemeColor('#e74c3c'); // Всё, где использовалась переменная, мгновенно перекрасится в красный!

25. Основы React: компоненты, JSX, props, state.
React - библиотека для построения UI на основе модели «состояние → представление»: компонент - чистая функция, отображающая props/state в дерево описаний UI (React-элементов). React берёт на себя синхронизацию этого дерева с реальным DOM через собственный планировщик и алгоритм согласования (reconciler, с React 16 - архитектура Fiber). Ниже - не просто синтаксис, а конкретная механика под каждым «удобством».

JSX - компиляция, а не магия браузера
JSX не выполняется браузером напрямую - это синтаксис, который на этапе сборки (Babel/SWC/esbuild) транслируется в вызовы функций:

const el = <div className="card">{title}</div>;
→
import { jsx as _jsx } from "react/jsx-runtime";
const el = _jsx("div", { className: "card", children: title });
	
	Production-следствие: JSX увеличивает объём собираемого бандла и требует шаг компиляции в CI - «просто HTML в JS» не существует без билд-пайплайна, это часть цены выбора React (в отличие от, например, HTMX или serverside-first подходов).
	Результат _jsx(...) - обычный JS-объект вида { type, props, key }. Отсюда правила:
Один корневой узел на возврат - функция возвращает одно значение (Fragment <>...</> решает это без лишнего DOM-узла).
className/htmlFor - потому что class/for - зарезервированные слова JS, а не разметки.
{выражение} - позиция для JS-выражения, не для операторов (if, for внутри {} не работают).

Компоненты и props: контракт данных
Компонент - функция, принимающая единственный аргумент props (объект с входными данными от родителя) и возвращающая описание UI (JSX).
Props - это и есть тот самый вход: значения, которые родительский компонент передаёт дочернему при использовании (<Card title="..." />), доступные внутри как поля объекта props.
function Card({ title, onSelect }) {
  return <div className="card" onClick={onSelect}>{title}</div>;
}

Однонаправленный поток данных. Props read-only для получателя = мутация объекта props компонентом является багом, а не стилем: изменение должно проходить через владельца состояния и колбэк, возвращаясь новым объектом props.
Class-компоненты - легаси. С React 16.8 (хуки) и тем более 18/19 функциональные компоненты - стандарт. Class-компоненты остаются нужны только там, где хуков ещё нет эквивалента: error boundaries (componentDidCatch/getDerivedStateFromError - до сих пор не переведены на хуки).
PropTypes - устаревшая практика для новых проектов. Проверка типов в рантайме дешевле статической не бывает; сейчас стандарт - TypeScript с типизацией props на этапе компиляции, без рантайм-оверхеда на каждый рендер.

State: точная механика, а не «где-то хранится»
Если props приходят снаружи и компонент их не меняет, то state - это данные, которыми компонент владеет сам: он может их менять во времени, и каждое такое изменение вызывает повторный рендер компонента с новым значением. useState - базовый хук для объявления такого состояния: он возвращает пару «текущее значение, функция для его изменения».
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
Как это устроено под капотом. Каждому компоненту в дереве соответствует узел Fiber - объект, а не просто «запись где-то в памяти», с полями stateNode, memoizedState, alternate (указатель на Fiber из предыдущего рендера для двойной буферизации). Хуки конкретного компонента образуют односвязный список (memoizedState → next → next…), подвешенный к его Fiber-узлу. useState при каждом вызове функции-компонента идёт по этому списку по порядку вызова, а не по имени переменной — именно поэтому существует "Rules of Hooks": условный или пропущенный вызов useState/useEffect сдвигает список и подставляет чужой хук другому слоту. Это не соглашение о стиле, а прямое следствие структуры данных.
setState не мутирует значение, а планирует работу. Вызов помечает Fiber как требующий обновления и ставит задачу в очередь планировщика (в конкурентном режиме React 18+ - с приоритетом: клик важнее фонового рендера). До завершения текущего рендера count в замыкании остаётся прежним.
Batching. До React 18 несколько setState объединялись в один ре-рендер только внутри React-обработчиков событий. С React 18 (createRoot, автоматический батчинг) это работает единообразно и в промисах, setTimeout, нативных listener'ах - важное отличие от ReactDOM.render, который остаётся в legacy-режиме без этой оптимизации. Использование устаревшего ReactDOM.render в 2026 году - bad practice именно по этой причине, не только «не модно».
Stale closure. Каждый рендер — новый вызов функции-компонента и новое замыкание над count. Асинхронный колбэк, созданный в рендере N, видит count рендера N, даже если реальное состояние успело уйти вперёд к моменту выполнения колбэка. Функциональная форма setCount(c => c + 1) обходит это, потому что React передаёт актуальное значение из очереди обновлений, а не из замыкания.
Иммутабельность коллекций в state - не стилистика, а требование алгоритма. React решает, нужен ли ре-рендер, через сравнение по ссылке (Object.is) между memoizedState предыдущего и нового значения. Мутация state.items.push(x) не создаёт новую ссылку → React не увидит изменения и не перерисует дерево, хотя данные в объекте реально изменились.

Reconciliation и Fiber: цена и границы
React не сравнивает деревья наивно попарно (это было бы O(n³) для общего случая деревьев) - эвристика: элементы разного type на одной позиции считаются полностью разными поддеревьями (старое размонтируется целиком, новое монтируется заново - сохранённый локальный state теряется), а списки сопоставляются по key.
key - стабильный идентификатор, по которому Fiber-узел старого рендера сопоставляется с новым при вставке/удалении в середине списка. Индекс массива как key работает, только если список статичен по порядку - при вставке/удалении происходит "переезд" state между визуально смещёнными, но логически разными элементами (заметно на контролируемых <input>). Trade-off, который стоит явно проговаривать: виртуальный DOM и reconciliation — это не бесплатное ускорение, а компромисс: overhead на построение и диффинг дерева объектов ради того, чтобы не думать вручную об императивных мутациях DOM. На простых статичных страницах прямая манипуляция DOM (или compile-time фреймворки вроде Svelte/SolidJS без виртуального DOM) может быть быстрее и легче. React выигрывает на сложном, часто меняющемся, стейтфул UI, а не в общем случае


Ошибки и грабли
Прямая мутация state (state.value = x, array.push) - компонент не перерисуется, потому что сравнение по ссылке не увидит изменения.
Индекс массива как key в изменяемых по составу списках - переезд state между элементами, особенно заметный на контролируемых полях ввода.
Stale closure - обращение к state в асинхронном колбэке (таймер, промис) без функциональной формы обновления возвращает значение из момента создания замыкания, а не актуальное.
Лишние ре-рендеры из-за нового объекта/функции в props на каждый рендер - инлайн () => {} или {...} литерал создаёт новую ссылку при каждом вызове родителя, что срывает React.memo на дочернем компоненте (мемоизация сравнивает props по ссылке); частая причина «memo не работает». Решается useCallback/useMemo, но и они не бесплатны - сами занимают память под кэш и требуют корректного массива зависимостей.
Ожидание, что setState применится синхронно сразу после вызова - из-за постановки в очередь планировщика и батчинга count сразу после setCount(count + 1) в том же обработчике всё ещё покажет старое значение.
Error boundary ловит не всё. Она перехватывает ошибки только во время рендера дерева (и только в компонентах ниже себя) - ошибки в обработчиках событий (onClick) или в асинхронном коде (fetch, setTimeout) через неё не проходят и требуют отдельного try/catch.

Главная идея: state в React - не «данные, которые где-то хранятся», а слот в связном списке хуков на Fiber-узле, идентифицируемый порядком вызова, а обновление - не мутация, а постановка работы в очередь планировщика. Из этой механики прямо следуют и правила хуков, и батчинг, и stale closures, и то, почему мемоизация и key - это не стилистические рекомендации, а инструменты управления конкретным алгоритмом сравнения по ссылке: React перерисовывает не то, что реально изменилось по смыслу, а то, у чего изменилась ссылка.

26. Жизненный цикл компонентов: методы жизненного цикла, хуки.
Компонент проходит три этапа: 
создание и появление на странице, 
обновление при изменении входных данных или внутреннего состояния, 
удаление со страницы. 
В старом (классовом) подходе для этого были отдельные методы под каждый этап. В современном подходе (функциональные компоненты) всё это объединяет один хук — эффект, который выполняется после отрисовки, а функция, которую он возвращает, отрабатывает при удалении компонента (аналог очистки). То, когда именно эффект перезапускается, определяется списком зависимостей рядом с ним: пустой список — сработает только один раз при появлении, без списка вообще — после каждой отрисовки, с указанными значениями — только когда они изменились.
Монтирование (mounting) — создание компонента и первое появление в DOM. Классовый метод: componentDidMount.
Обновление (updating) — перерисовка из-за изменения props или state. Классовый метод: componentDidUpdate.
Размонтирование (unmounting) — удаление компонента со страницы. Классовый метод: componentWillUnmount.
В хуках useEffect(() => {...}, [deps]) тело функции покрывает монтирование и обновление, а return () => {...} внутри — это размонтирование (аналог очистки перед уходом компонента).
Подвох: если оставить список зависимостей пустым, а внутри эффекта использовать значение, которое может измениться, — эффект продолжит работать со старым, устаревшим значением этой переменной.

27. React Hooks.
React Hooks - это специальные функции, появившиеся в React 16.8, которые позволяют использовать состояние (state), жизненный цикл компонента и другую функциональность React в функциональных компонентах. До появления Hooks для этого использовались преимущественно классовые компоненты, однако сегодня в современной разработке практически все новые проекты строятся на функциональных компонентах с использованием Hooks.
Главная идея Hooks заключается в том, что они позволяют хранить состояние и выполнять побочные действия без использования классов, делая код проще, компактнее и удобнее
Хуки позволяют функциональным компонентам использовать стейт и жизненный цикл React.
Наиболее часто используются следующие Hooks:
– useState - хранит состояние компонента. Например, количество товаров в корзине, текст, введенный пользователем, или состояние открытия меню.
– useEffect - выполняет побочные действия: отправку HTTP-запросов, работу с таймерами, подписку на события или обновление документа после изменения состояния.
– useContext - предоставляет доступ к общим данным приложения без передачи их через множество компонентов (например, тема оформления или информация о пользователе).
– useRef - позволяет получить ссылку на DOM-элемент или сохранить значение между перерисовками без повторного рендера.
– useMemo и useCallback - используются для оптимизации производительности, предотвращая ненужные вычисления и создание новых функций при каждом рендере.
Два главных правила хуков 
React должен точно знать, какой хук к какому состоянию относится при каждом рендере. Из-за того, как React устроен под капотом (он отслеживает хуки по порядку их вызова), существуют два железных правила:
1 Вызывайте хуки только на самом верхнем уровне. Нельзя вызывать хуки внутри циклов, условий (if) или вложенных функций. Вызовы всегда должны происходить в одном и том же порядке при каждом рендере компонента.
2 Вызывайте хуки только из функций React. Либо из функциональных компонентов, либо из ваших собственных кастомных хуков. Из обычных JS-функций вызывать их нельзя.

useState - Этот хук позволяет функциональному компоненту иметь свою "память":
import React, { useState } from 'react';


function Counter() {
 // useState возвращает массив: [текущее_значение, функция_для_его_изменения]
 const [count, setCount] = useState(0); // 0 — начальное состояние


 return (
   <div>
     <p>Вы кликнули {count} раз</p>
     <button onClick={() => setCount(count + 1)}>
       Кликни меня
     </button>
   </div>
 );
}
Когда ты вызываешь setCount, React не просто меняет переменную — он запускает ререндер компонента. Компонент выполняется заново, но useState возвращает уже обновленное значение count.

useEffect - то всё, что выходит за рамки простого рендеринга интерфейса: запросы к API, подписки на события, ручное изменение DOM, таймеры.
import React, { useState, useEffect } from 'react';


function UserProfile({ userId }) {
 const [user, setUser] = useState(null);
 useEffect(() => {
   // 1. Код эффекта (срабатывает при монтировании и изменении userId)
   let isMounted = true;
   fetch(`https://api.example.com/users/${userId}`)
     .then(res => res.json())
     .then(data => {
       if (isMounted) setUser(data);
     });
   // 2. Функция очистки (Cleanup function)
   return () => {
     isMounted = false; // Предотвращает утечку памяти, если компонент размонтировался до конца запроса
   };
 }, [userId]); // 3. Массив зависимостей (Dependency Array)
 if (!user) return <div>Загрузка...</div>;
 return <h1>{user.name}</h1>;
}
Пустой массив []: Эффект выполнится один раз при монтировании компонента (аналог componentDidMount).
Массив с переменными [userId]: Эффект выполнится при монтировании И каждый раз, когда меняется userId.
Без массива вовсе (забыли указать): Эффект будет срабатывать при каждом рендере компонента. Это частая причина бесконечных циклов запросов к серверу и зависания вкладки браузера.

useRef - Ссылка на DOM или хранение данных без рендеринга.
У useRef есть две ключевые суперсилы:
Доступ к реальному DOM-узлу (например, чтобы программно сфокусировать инпут или запустить видео).
Хранение изменяемой переменной, изменение которой не должно вызывать повторный рендер компонента (в отличие от useState).
import React, { useRef } from 'react';


function TextInputWithFocusButton() {
 const inputEl = useRef(null); // Создаем ссылку
 const onButtonClick = () => {
   // .current указывает на смонтированный элемент <input>
   inputEl.current.focus();
 };
 return (
   <>
     {/* Привязываем ссылку к элементу */}
     <input ref={inputEl} type="text" />
     <button onClick={onButtonClick}>Установить фокус на инпут</button>
   </>
 );
}

28. Управление состоянием.
useState внутри одного компонента решает локальную задачу, но реальные приложения быстро упираются в вопрос: где хранить состояние, которое нужно нескольким компонентам сразу, и как до него достучаться без излишней связанности. «Управление состоянием» - это набор паттернов и инструментов для ответа на этот вопрос, и выбор между ними - это выбор конкретных компромиссов, а не «лучшей практики».
  Локальное состояние и подъём состояния (lifting state up)
Если состояние нужно только одному компоненту - оно должно жить в нём (useState/useReducer) и нигде больше; хранить его выше «на всякий случай» без необходимости - источник лишних ре-рендеров и усложнения. Когда состояние нужно двум и более компонентам с общим предком, стандартный первый шаг - поднять его к ближайшему общему предку и передать вниз через props вместе с колбэками для изменения.
Это работает, пока дерево неглубокое. На глубине в несколько уровней подъём превращается в prop drilling - проброс props через промежуточные компоненты, которым сами эти данные не нужны, а нужны только их потомкам. Prop drilling - не баг, а нормальный первый признак того, что состояние пора вынести из локального дерева props в отдельный механизм.

Context API: что он решает и чего не решает
createContext + useContext избавляют от прокидывания props через промежуточные уровни: Provider кладёт значение в дерево, любой потомок читает его напрямую через useContext, минуя всех, кто между ними.

const ThemeContext = createContext(null);

function App() {
  const [theme, setTheme] = useState("dark");
  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      <Page />
    </ThemeContext.Provider>
  );
}

Ключевой механизм, который часто упускают: Context не оптимизирует ре-рендеры - он лишь избавляет от явного прокидывания props. Когда значение Provider меняется, React перерисовывает все компоненты, вызывающие useContext этого контекста, независимо от того, какой конкретно кусок объекта-значения они реально используют. Если в один контекст положить и часто меняющееся значение, и редко меняющееся, потребители второго будут перерисовываться при каждом изменении первого - это не оптимизация, а просто другой способ передачи данных, с собственной ценой.
Из этого следует практическое правило: разделять контексты по частоте изменения (например, отдельный контекст для темы и отдельный для данных пользователя) и не использовать Context как замену полноценному стору с избирательной подпиской для часто меняющихся данных - это разные инструменты по своей механике.

Внешние стейт-менеджеры: разные модели подписки
Библиотеки управления состоянием решают именно то, чего не решает Context: избирательный ре-рендер только тех компонентов, которые подписаны на конкретный изменившийся кусок состояния, а не на весь стор целиком.

Zustand - минимальный API, стор - обычная функция вне React, подписка через селектор внутри хука; меньше церемоний, но меньше встроенной структуры для больших команд.
Jotai/Recoil  состояние строится снизу вверх из мелких независимых атомов, а не одного большого объекта; хорошо ложится на несвязанные друг с другом куски UI-состояния, но для сильно взаимозависимых данных единый стор иногда нагляднее.

Общий для всех trade-off: любой внешний стор - это состояние вне дерева React, а значит, и вне жизненного цикла компонентов; ответственность за корректную очистку подписок и за то, чтобы стор не рос бесконтрольно, лежит на разработчике, а не на React.

Серверное состояние - отдельная категория
Ключевое разделение, которое часто не проводят явно: клиентское состояние (UI-состояние - открыт ли модал, значение поля ввода) и серверное состояние (данные, полученные с бэкенда) - принципиально разные вещи, и решать их одним и тем же инструментом неэффективно.
Серверные данные не принадлежат клиенту целиком: они могут устареть в любой момент (кто-то другой изменил их на сервере), их нужно кэшировать, повторно запрашивать при необходимости, обрабатывать состояния загрузки/ошибки и дедуплицировать параллельные запросы одних и тех же данных. Хранить их в Redux/Context как обычный клиентский state означает вручную реализовывать всё это самостоятельно.
Инструменты вроде TanStack Query (React Query) и SWR решают именно эту задачу: кэш с привязкой к ключу запроса, автоматическая ревалидация (в том числе по паттерну stale-while-revalidate - сразу показать закэшированное значение и обновить его в фоне), дедупликация параллельных запросов, автоматические isLoading/isError без ручного управления флагами. Итог - в современных React-приложениях типичное разделение: серверные данные живут в query-кэше отдельной библиотеки, а Redux/Zustand/Context остаются для UI-состояния, которого заметно меньше, чем принято было считать до появления этих инструментов.

Типичные ошибки
Один большой контекст под всё состояние приложения. Любое изменение любого поля перерисовывает всех потребителей - та самая механика Context, о которой сказано выше, здесь проявляется максимально болезненно.
Дублирование серверных данных в глобальном сторе вручную, без библиотеки кэширования - на практике превращается в самописную и обычно неполную реализацию кэша, инвалидации и обработки гонок запросов.
Подъём состояния выше, чем нужно, «на будущее» - увеличивает зону ре-рендера и число компонентов, зависящих от состояния, которое реально нужно только листовому компоненту.
Селектор в Redux/Zustand, возвращающий новый объект на каждый вызов (например, { a: state.a, b: state.b } без мемоизации) - воспринимается как изменение по ссылке даже без реального изменения данных, и подписанный компонент перерисовывается впустую.
Выбор тяжёлого стора для локальной задачи одного дерева компонентов - если состояние нужно только двум-трём компонентам с общим предком, простой подъём state обычно проще и понятнее, чем подключение внешней библиотеки.

Главная идея: управление состоянием - это не один инструмент на все случаи, а выбор между разными моделями подписки на изменения. Context устраняет прокидывание props, но не ре-рендер - перерисовывает всех потребителей целиком; внешние сторы (Redux, Zustand, Jotai) добавляют избирательную подписку на конкретный кусок состояния; а серверные данные - отдельная категория со своими требованиями (кэш, ревалидация, дедупликация), для которой существуют специализированные инструменты, а не обобщённый стор состояния.
29. Маршрутизация.
Маршрутизация (Routing) в React относится к процессу определения, какие компоненты отображать пользователю в зависимости от текущего URL-адреса в браузере. В отличие от традиционных многостраничных приложений, React-приложения обычно являются одностраничными приложениями (Single Page Applications, SPA). Это означает, что весь контент загружается на одной HTML-странице, а переход между “страницами” происходит динамически, без полной перезагрузки. Маршрутизация позволяет SPA имитировать поведение многостраничных сайтов, предоставляя пользователю ощущение навигации между различными представлениями. 
В React нет встроенного решения для маршрутизации, поэтому для этой цели используются сторонние библиотеки. Наиболее популярной и часто используемой является React Router.
Механизм работы 
В отличие от многостраничного приложения, при клиентской маршрутизации HTTP-запрос нового HTML на каждый переход не выполняется. Изменяются location (URL) и дерево React-компонентов в уже загруженном документе.
BrowserRouter использует HTML5 History API: history.pushState, history.replaceState и событие popstate. При переходе через Link обработчик предотвращает действие браузера по умолчанию (preventDefault у <a>) и записывает новый URL в историю через pushState. Документ не перезагружается. Роутер обновляет объект location, хранимый в React Context, после чего подписчики (в том числе Routes) выполняют повторное сопоставление pathname с конфигурацией маршрутов и монтируют соответствующий element.
При нажатии кнопок «назад» / «вперёд» браузер генерирует popstate. BrowserRouter синхронизирует location с window.location и инициирует повторный рендер. Программная навигация через useNavigate использует тот же механизм изменения истории и обновления контекста.
Клиентская маршрутизация действует только после загрузки приложения в браузер. Переход по Link с / на /about не порождает запрос нового HTML к серверу — URL изменяется через History API, React Router выполняет matching и монтирует соответствующий компонент. Иная ситуация - открытие или обновление документа по адресу https://example.com/about. Браузер отправляет HTTP-запрос пути /about на сервер. Отдельного ресурса /about на сервере обычно нет, путь является клиентским маршрутом. При отсутствии специальной конфигурации возвращается HTTP 404. Для SPA задаётся fallback - на неизвестные пути отдаётся тот же index.html, что и на корень. После загрузки JS React Router читает pathname /about и монтирует нужный экран.
Альтернатива - HashRouter. Маршрут размещается в hash-части URL, например https://example.com/#/about. На сервер уходит запрос только к /, фрагмент #/about обрабатывается в браузере. Fallback на index.html для глубоких путей не требуется, однако форма URL менее удобна. В production применяется BrowserRouter при настроенном серверном fallback под History API.
Основные компоненты React Router
BrowserRouter – корневой провайдер для веб-приложений. Инициализирует history на базе HTML5 History API и передаёт location через Context дочерним компонентам.
Routes – контейнер набора Route. Выполняет matching текущего URL и рендерит подходящий маршрут. В v6 заменяет Switch из предыдущих версий API.
Route – описание отдельного маршрута. Основные props: path (шаблон пути) и element (React-элемент для рендера при совпадении).
Link – навигационная ссылка внутри SPA. Изменяет URL через History API без полной перезагрузки. В отличие от нативного <a href>, не инициирует новый document request.
NavLink – расширение Link с индикацией активного состояния при совпадении to с текущим location (стилизация активного пункта навигации).
import { BrowserRouter, Routes, Route, Link } from 'react-router-dom';


function App() {
 return (
   <BrowserRouter>
     <nav>
       <Link to="/">Главная</Link>
       <Link to="/about">О проекте</Link>
     </nav>
     <Routes>
       <Route path="/" element={<HomePage />} />
       <Route path="/about" element={<AboutPage />} />
       <Route path="*" element={<NotFoundPage />} />
     </Routes>
   </BrowserRouter>
 );
}


Маршрут path="*" используется как fallback при отсутствии совпадений (обработка 404).
Динамические параметры и программная навигация. Сегмент пути задаётся префиксом : в path, например /products/:productId. Значения параметров извлекаются хуком useParams, возвращающим объект пар «имя параметра — значение».
Программная навигация (после аутентификации, submit формы, проверки прав) выполняется хуком useNavigate. Возвращаемая функция изменяет location без участия Link; внутренне применяется тот же History API.
const navigate = useNavigate();
navigate('/dashboard');


Вложенные маршруты описывают иерархию URL и UI. Родительский Route рендерит layout-компонент; дочерние маршруты отображаются в позиции Outlet. Это устраняет дублирование общего каркаса (меню, sidebar) при смене подразделов. URL отражает вложенность (/dashboard/settings, /dashboard/profile). Представление по умолчанию на уровне родителя задаётся через index-маршрут.

30. Формы.
Формы - это механизм взаимодействия пользователя с веб-приложением. С их помощью пользователь вводит данные, которые затем могут быть отправлены на сервер или обработаны непосредственно в браузере. Формы используются при регистрации, авторизации, поиске, оформлении заказов, заполнении анкет и во многих других сценариях.
Фундаментальное отличие HTML подхода от React
В веб-разработке работа с формами всегда сводится к одному вопросу: Кто сейчас владеет состоянием, которое ввел пользователь?
– HTML (Неуправляемый подход / Uncontrolled): Источником правды является сам DOM (браузер). Текстовое поле само хранит внутри себя строку, которую вы туда ввели. Чтобы получить эти данные, нам нужно пойти в DOM и "спросить" элемент о его значении (например, через document.getElementById().value или объект FormData при отправке).
– React (Управляемый подход / Controlled): Источником правды является состояние компонента (State). Каждое нажатие клавиши перехватывается, отправляется в React State, а React затем принудительно обновляет значение (value) в DOM. Браузер больше ничем не владеет - он лишь послушно отображает то, что ему приказал React.
Реализация формы через HTML:
<form action="/api/v1/login" method="POST" id="loginForm">
 <label for="emailInput">Email:</label>
 <input
   type="email"
   id="emailInput"
   name="email"
   placeholder="user@example.com"
   required
 />
 <button type="submit">Войти</button>
</form>
action ("/api/v1/login"): URL-адрес, куда браузер отправит данные формы при клике на кнопку отправки. Если не указать, форма отправится на текущий URL.
method ("POST"): HTTP-метод для отправки данных (обычно GET или POST).
name ("email"): Критически важный атрибут. Это ключ, под которым значение инпута улетит на сервер (в формате email=значение). Без атрибута name данные из этого input вообще не будут отправлены.
type ("email"): Включает базовую валидацию силами браузера (проверка на символ @) и адаптирует экранную клавиатуру на мобильных устройствах.
required (HTML5 валидация): Запрещает отправку формы, если поле пустое. Работает на уровне браузера.

Реализация формы в React
В React мы отказываемся от стандартного поведения браузера. Мы перехватываем отправку (onSubmit), отменяем дефолтную перезагрузку страницы (preventDefault()) и синхронизируем ввод пользователя с состоянием React.
import React, { useState } from 'react';


function LoginForm() {
 const [email, setEmail] = useState('');
 const handleSubmit = (event) => {
   event.preventDefault(); // Остановка стандартного поведения браузера
   console.log('Данные отправлены на сервер:', { email });
   // Здесь мы вызываем fetch/axios API
 };


 return (
   <form onSubmit={handleSubmit}>
     <label htmlFor="emailInput">Email:</label>
     <input
       type="email"
       id="emailInput"
       value={email}
       onChange={(event) => setEmail(event.target.value)}
       placeholder="user@example.com"
     />
     <button type="submit">Войти</button>
   </form>
 );
}
onSubmit={handleSubmit}: Вместо action мы вешаем JS-обработчик. Браузер не перезагружает страницу, отправкой данных управляем мы сами через асинхронные запросы (AJAX/Fetch).
htmlFor (вместо for): В React используется camelCase для атрибутов, а слово class и for являются зарезервированными в JS, поэтому для связки лейбла с инпутом используется htmlFor.
value={email}: Мы связываем значение инпута с переменной состояния email. Теперь инпут не может показать ничего, кроме того, что записано в переменной email.
onChange={...}: Слушатель события изменения. Как только пользователь нажал клавишу, срабатывает функция, которая обновляет стейт (setEmail). Стейт обновляется -> компонент рендерится заново -> в value передается новое значение -> пользователь видит изменения.

31. Работа с API: Fetch, Axios, обработка ошибок.
Клиентский код обращается к серверу асинхронно и должен корректно обработать три разных типа сбоя: сеть недоступна, сервер ответил с кодом ошибки, ответ пришёл, но не в ожидаемом формате. Fetch и Axios решают это по-разному, и большинство багов в работе с API - следствие того, что эту разницу не учли.
Fetch: встроенный API с неочевидным контрактом
fetch — нативный браузерный API, промис-обёртка над HTTP-запросом, ничего дополнительно устанавливать не нужно.

const response = await fetch("/api/users/1");
const data = await response.json();

Ключевой и самый частый источник багов: промис, возвращаемый fetch, не отклоняется (reject) при HTTP-статусах 4xx/5xx - с точки зрения fetch, сервер ответил, значит запрос выполнен успешно на транспортном уровне. Отклонение промиса происходит только при реальном сбое сети (недоступен DNS, обрыв соединения, CORS-блокировка). Поэтому проверка статуса - обязательная ручная операция:
const response = await fetch("/api/users/1");
if (!response.ok) {          // response.ok === (status >= 200 && status < 300)
  throw new Error(`HTTP ${response.status}`);
}
const data = await response.json();


Код без этой проверки будет пытаться парсить тело ответа 404/500 как успешный JSON вместо явной обработки ошибки - типичная причина «тихих» багов в проде.
Другие особенности контракта:
response.json()/.text() - тоже асинхронны и могут упасть отдельно (сервер прислал не-JSON с заголовком application/json) - это третий тип ошибки, отдельный от сетевой и от HTTP-статуса.
Тело ответа можно прочитать только один раз - повторный вызов .json() на том же Response бросит исключение; если нужно прочитать дважды, используйте response.clone().
Нет встроенного таймаута. fetch не отменяет запрос по времени сам - это нужно реализовывать явно.
Нет автоматической сериализации/десериализации JSON для запроса - заголовок Content-Type и JSON.stringify(body) для тела запроса нужно выставлять вручную.

	Axios: обёртка с другим контрактом по умолчанию
	Axios - сторонняя библиотека (в браузере работает поверх XMLHttpRequest, в Node.js - поверх http/https), решающая именно те неудобства, которые у fetch приходится закрывать вручную.

const { data } = await axios.get("/api/users/1");

Ключевые отличия от fetch:
По умолчанию отклоняет промис на статусах вне 2xx - не нужно вручную проверять response.ok, поведение интуитивнее «из коробки» (настраивается через validateStatus, если нужно иное).
Автоматическая (де)сериализация JSON - data уже разобранный объект, а не строка, которую нужно отдельно парсить; для запроса Content-Type и JSON.stringify подставляются сами.
Интерцепторы (interceptors) - глобальные хуки на все запросы/ответы: удобно для сквозной подстановки токена авторизации, единообразного логирования, централизованной обработки 401 (например, автоматический refresh токена и повтор запроса).
Встроенный таймаут - параметр timeout в конфиге запроса, не нужно вручную комбинировать с AbortController.
Автоматическая отмена дублирующихся/устаревших запросов через AbortController, который Axios поддерживает как обёртку (в старых версиях был собственный CancelToken, сейчас - сходится к стандартному API).

Trade-off: fetch - ноль зависимостей и полный контроль над поведением, но требует больше шаблонного кода на каждый запрос (проверка статуса, таймаут, повторное чтение тела). Axios снимает этот шаблонный код и даёт единообразную обработку ошибок через интерцепторы, но это дополнительная зависимость в бандле и своя (пусть и более предсказуемая) модель ошибок, которую тоже нужно знать.

Обработка ошибок: три разных источника
Правильная обработка различает, где именно произошёл сбой, а не ловит всё одним общим catch:
Сетевая ошибка - запрос не дошёл до сервера или обратно (нет соединения, DNS, CORS). У fetch это TypeError в catch; у Axios - ошибка без error.response (error.request есть, ответа нет).
HTTP-ошибка - сервер ответил, но со статусом ошибки. У fetch нужно проверять response.ok вручную; у Axios это уже catch с заполненным error.response.status.
Ошибка формата данных - ответ пришёл успешным по статусу, но тело не парсится или не соответствует ожидаемой структуре (например, бэкенд вернул HTML вместо JSON из-за упавшего прокси). Отдельный try/catch вокруг парсинга или валидация структуры (например, через Zod/io-ts) до того, как данные попадут в остальной код.

Практический паттерн - не пробрасывать «сырую» ошибку до UI, а нормализовать в собственный класс с понятным пользователю сообщением и сохранённым исходным статусом/причиной для логирования:

class ApiError extends Error {
  constructor(message, status, cause) {
    super(message);
    this.status = status;
    this.cause = cause;
  }
}

Отмена запросов и таймаут
AbortController - стандартный способ отменить запрос (актуально и для fetch, и поддерживается Axios):

const controller = new AbortController();
const timeoutId = setTimeout(() => controller.abort(), 5000);

try {
  const response = await fetch(url, { signal: controller.signal });
  clearTimeout(timeoutId);
} catch (err) {
  if (err.name === "AbortError") { /* таймаут или ручная отмена */ }
}
Отмена нужна не только для таймаута, но и для отмены запроса при размонтировании компонента или при повторном запуске того же запроса до завершения предыдущего - без неё завершившийся позже устаревший запрос может перезаписать более новые данные (см. ниже).

Гонка запросов (race condition)
Если пользователь быстро меняет параметры запроса (например, вводит текст в поле поиска, каждое изменение шлёт новый запрос), запросы уходят в сеть в одном порядке, но могут завершиться в другом - сеть не гарантирует порядок ответов. Без явной защиты последний завершившийся ответ перезапишет состояние, даже если он относится к устаревшему, уже неактуальному запросу.
Решения: отмена предыдущего запроса перед стартом нового (AbortController), либо проверка на момент получения ответа, что он всё ещё соответствует последнему отправленному запросу (сравнение идентификатора/параметров), либо использование библиотеки данных с этим встроенным (например, TanStack Query автоматически игнорирует устаревшие ответы по ключу запроса).

Повторные попытки (retry)
Не каждая ошибка должна тут же показываться пользователю - временный сетевой сбой или 503 разумно повторить с задержкой. Важные принципы: повторять только идемпотентные операции по умолчанию (GET безопасен, POST - не всегда, если не гарантирована идемпотентность на сервере через ключ идемпотентности), использовать экспоненциальный backoff вместо мгновенных повторов подряд (иначе retry-шторм только усугубляет перегруженный сервер), и ограничивать число попыток.

Типичные ошибки
Не проверять response.ok у fetch - самая частая ошибка именно из-за неочевидного контракта: код думает, что раз промис не упал, значит запрос успешен.
Ловить всё одним catch без различения источника ошибки - невозможно показать пользователю осмысленное сообщение («нет интернета» vs «сервер вернул 403»), если ошибка не типизирована.
Забытый таймаут - запрос к недоступному серверу без AbortController+setTimeout может висеть неограниченно долго, замораживая UI в состоянии загрузки.
Гонка запросов без отмены - устаревший ответ перезаписывает актуальные данные, воспроизводится нестабильно и трудно отлаживается, потому что зависит от таймингов сети.
Повтор неидемпотентных запросов вслепую - автоматический retry POST-запроса создания сущности без ключа идемпотентности может задвоить запись на сервере.
Логирование чувствительных данных при обработке ошибок - тело запроса с паролем/токеном, попавшее в лог ошибки целиком, - утечка данных под видом отладочной информации.

Главная идея: fetch и Axios расходятся в одном принципиальном месте - контракте отклонения промиса на HTTP-ошибках, - и большинство багов работы с API растёт именно оттуда. Надёжная обработка ошибок различает сетевой сбой, HTTP-статус и ошибку формата данных как три разных случая, а не один общий catch, и учитывает, что сеть не гарантирует ни доставку в разумное время (нужен таймаут), ни порядок ответов (нужна защита от гонки запросов).

32. Оптимизация производительности в React приложениях.
Основные приёмы: 
обёртка компонента, которая пропускает его повторную отрисовку, если входные данные не изменились; 
запоминание результата дорогого вычисления между отрисовками, чтобы не пересчитывать его каждый раз без надобности; 
запоминание самой функции-обработчика между отрисовками, чтобы не создавать её заново (важно при передаче в дочерний компонент, который сам пропускает повторную отрисовку — иначе он всё равно перерисуется из-за «новой» функции). 
Для длинных списков используют отрисовку только видимых элементов, а не всех сразу. Для больших приложений — загрузку кода частями, по мере реальной необходимости, а не всего сразу при старте.
Подвох: у элементов списка обязателен уникальный устойчивый идентификатор — использование порядкового номера элемента в этом качестве плохая практика, если список может менять порядок или состав: это приводит не просто к лишним перерисовкам, а к реальным багам — компонентам «путается» состояние между элементами.


33. Тестирование React приложений
СПАСИБО ЗА ВОПРОС
Главная ошибка, которую совершают команды - тестировать реализацию, а не поведение. Тест, который проверяет «в state лежит isOpen: true», сломается при любом рефакторинге, даже если приложение работает идеально. Тест, который проверяет «после клика по кнопке пользователь видит модальное окно», переживёт переезд со стейта на редьюсер, с классового компонента на хуки и даже частично - смену UI-библиотеки.
Отсюда центральный принцип современного тестирования React: Чем больше ваши тесты похожи на то, как приложением пользуются реальные люди, тем больше уверенности они дают.
Для фронтенда актуален Testing Trophy:
Static (основание) - TypeScript, ESLint. Ловят целый класс ошибок бесплатно, ещё до запуска кода. Типизация - это тоже тестирование.
Unit - чистые функции: утилиты, форматтеры, редьюсеры, кастомные хуки со сложной логикой. Быстрые, дешёвые, но проверяют кусочки в изоляции.
Integration (самая «мясистая» часть трофея) - компонент или страница целиком: рендерим, кликаем, вводим текст, проверяем результат. Именно здесь оптимальное соотношение «уверенность / стоимость». Большинство React-тестов в production-проектах - это они.
E2E (вершина) - реальный браузер, реальный (или почти реальный) бэкенд. Максимальная уверенность, максимальная цена: медленные, флакающие, дорогие в поддержке. Покрываем ими только критические пользовательские сценарии: логин, оформление заказа, оплата.

Инструменты production-уровня
Test runner: Vitest (или Jest)
Jest - многолетний стандарт: раннер, ассерты, моки и coverage в одной коробке. 
Vitest - его современная замена: тот же API (миграция почти бесплатная), но нативная поддержка ESM и TypeScript, общий конфиг с Vite и заметно быстрее. В новых проектах на Vite выбор по умолчанию - Vitest; Jest остаётся в легаси и экосистеме CRA/Next.
Раннер даёт три ключевые вещи: describe/it для структуры, expect для ассертов и систему моков.
Рендеринг и запросы: React Testing Library (RTL)
RTL - стандарт де-факто, победивший Enzyme именно потому, что физически не даёт лезть во внутренности компонента. Никакого доступа к state и props - только то, что видит пользователь.
Ключевая идея - приоритет запросов (queries): ищем элементы так, как их находит человек (и скринридер):
// Хорошо: по роли и доступному имени — так элемент видит пользователь
screen.getByRole('button', { name: /отправить/i })
screen.getByLabelText(/email/i)


// Допустимо, если роли нет
screen.getByText(/заказ оформлен/i)


// Последнее средство — признак, что у вёрстки проблемы с доступностью
screen.getByTestId('submit-btn')
Бонус: такие тесты попутно проверяют accessibility. Если getByRole не находит кнопку - возможно, у вас <div onClick>, и это баг сам по себе.
Три семейства запросов: getBy* (элемент должен быть - иначе ошибка), queryBy* (проверяем отсутствие), findBy* (ждём появления - для асинхронщины).
Симуляция действий: user-event
Не fireEvent.click(), а userEvent.click(). Разница принципиальна: fireEvent диспатчит одно синтетическое событие, а user-event воспроизводит полную цепочку, как у реального пользователя (hover → mousedown → focus → mouseup → click). 
const user = userEvent.setup();
await user.type(screen.getByLabelText(/email/i), 'dev@example.com');
await user.click(screen.getByRole('button', { name: /войти/i }));
expect(await screen.findByText(/добро пожаловать/i)).toBeInTheDocument();
Мокирование сети: MSW (Mock Service Worker)
Ключевой инструмент, отличающий зрелый подход. Плохая практика - мокать axios или fetch (vi.mock('axios')): тест начинает знать, как компонент ходит в сеть, и ломается при смене HTTP-клиента или переезде на React Query.
MSW перехватывает запросы на сетевом уровне. Компонент делает настоящий запрос - MSW отвечает замоканными данными:
const server = setupServer(
 http.get('/api/user', () => HttpResponse.json({ name: 'Anna' })),
);
E2E: Playwright (или Cypress)
Playwright - текущий фаворит индустрии: все браузерные движки (Chromium, Firefox, WebKit), настоящая параллельность, авто-ожидания, трейсы с записью каждого шага для отладки упавших тестов в CI. 
Cypress - зрелая альтернатива с отличным интерактивным UI, но с ограничениями по браузерам и параллелизации (платной).

Типовой production-стек и структура теста
Стек здорового проекта в 2026 году: Vitest + React Testing Library + user-event + MSW + Playwright, всё в CI на каждый pull request.
