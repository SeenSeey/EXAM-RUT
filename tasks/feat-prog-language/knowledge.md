Концептуальные особенности языков программирования
1. Парадигмы программирования: императивное, объектно-ориентированное, функциональное, процедурное.
Парадигма программирования - это набор идей, понятий, правил и принципов, определяющих стиль написания кода и способ организации вычислений. Это, по сути, призма или свод правил, через которые разработчик смотрит на задачу.
Важно понимать, что современные языки редко относятся только к одной парадигме. Например:
– Python - процедурный, объектно-ориентированный и функциональный;
– C++ - процедурный и объектно-ориентированный (а также поддерживает элементы функционального программирования);
– Java - объектно-ориентированный с функциональными возможностями;
– JavaScript - поддерживает практически все перечисленные подходы.
Поэтому обычно говорят не «язык X - объектно-ориентированный», а «язык X поддерживает ООП».
1. Императивное программирование
Программа представляет собой последовательность команд, изменяющих состояние памяти.
Пример:
x = 5
y = 10
sum = x + y
print(sum)
2. Процедурное программирование
Вместо одного длинного алгоритма создаются небольшие блоки, каждый из которых решает одну задачу.
Пример:
def square(x):
   return x * x
number = 5
result = square(number)
print(result)
3. Объектно-ориентированное программирование (ООП)
Вместо набора функций программа строится из объектов. Объект объединяет: данные (поля); поведение (методы).
Четыре основных принципа ООП:
Инкапсуляция. Объединение данных и методов внутри объекта и сокрытие внутренней реализации.
Наследование. Позволяет создавать новый класс на основе существующего.
Полиморфизм. Одинаковый интерфейс - разное поведение.
Абстракция. Выделение только важных характеристик объекта, скрывая детали реализации.
4. Функциональное программирование
Функциональный подход отвечает на вопрос: "Какое значение должна вернуть функция?"
Главная особенность - не изменять данные, а получать новые. 
Желательно использовать чистые функции.

Чистая функция -  это функция, которая всегда возвращает одинаковый результат для одинаковых аргументов и не изменяет внешнее состояние.
Пример:
numbers = [1, 2, 3, 4]
squares = list(map(lambda x: x * x, numbers))
print(squares)
Исходный список остаётся неизменным.


2. Типизация: статическая и динамическая, сильная и слабая.
Главное, что нужно понимать: «статическая/динамическая» и «сильная/слабая» - это две независимые (ортогональные) оси, а не концы одного спектра. Первая ось отвечает на вопрос, когда проверяются типы, вторая - насколько строго они соблюдаются. Их часто путают, и именно чёткое разделение этих осей отличает поверхностное понимание от глубокого.

Статическая и динамическая типизация
Эта ось определяет момент проверки типов.
При статической типизации типы известны и проверяются до выполнения, на этапе компиляции; тип связан с переменной, а не только со значением (C, C++, Java, C#, Go, Rust, Kotlin, Scala, Haskell, TypeScript).
При динамической типизации проверка происходит во время выполнения: тип несёт само значение (его «тег»), а переменная - лишь ссылка на него (Python, Ruby, JavaScript, PHP, Lisp).
Ключевые понятия этой оси:
Явная и выводимая типизация - статическая типизация не означает многословность. При выводе типов компилятор восстанавливает их сам: полный вывод по Хиндли–Милнеру (Haskell, OCaml, F#) или локальный (Rust, Go, C++ auto, Java var).
Номинальная и структурная типизация - совместимость определяется либо именем типа (Java, C#), либо его формой, набором полей и методов (Go-интерфейсы, TypeScript).
Утиная типизация (duck typing) - динамический структурный подход: важно не имя типа, а наличие нужных методов (Python, Ruby).

Сильная и слабая типизация
Эта ось описывает строгость соблюдения типов. Важно понимать, что у неё нет строгого формального определения - это неформальный спектр, описывающий, насколько язык допускает неявные приведения.
Сильная типизация не даёт молча выполнять бессмысленные операции и требует явных преобразований. Пример: "5" + 3 в Python — это TypeError.
Слабая типизация допускает неявные приведения, иногда с переинтерпретацией самого представления данных: приведение указателей и void*/union в C, коэрции в JavaScript ("5" + 3 даёт "53"), «магия» сравнений в PHP.
Ортогональность двух осей нагляднее всего в матрице 2×2:

Главная идея: типизация описывается двумя независимыми осями - когда проверяются типы (статика/динамика) и насколько строго они соблюдаются (сила/слабость). «Сильная/слабая» - неформальный спектр про неявные приведения, а не про наличие компилятора; настоящий же водораздел в статике проходит по соундности, выводу типов и мощности системы типов вплоть до аффинных и зависимых.

3. Компилируемые и интерпретируемые языки.
Компиляция – однократный перевод всей программы с исходного языка в целевой (обычно машинный код) специальной программой-компилятором ещё до запуска программы. Результат – самостоятельный исполняемый файл, который затем можно запускать сколько угодно раз без повторного перевода.
Пример: C, C++, Go, Rust
Интерпретация – построчное (или инструкция за инструкцией) чтение и непосредственное выполнение исходного кода (или его промежуточного представления) программой-интерпретатором непосредственно во время работы программы, без создания отдельного исполняемого файла.
Пример: Python, JS, PHP, Ruby
Транслятор – общий термин для программы, переводящей текст с одного языка на другой; компилятор и интерпретатор — оба являются трансляторами, но с разной стратегией: компилятор переводит весь текст сразу и заранее, интерпретатор — по частям и в момент исполнения.
Java и C# не являются ни чисто компилируемыми, ни чисто интерпретируемыми – это гибрид: компиляция в байт-код + виртуальная машина + JIT.
Байт-код – промежуточное, платформонезависимое представление программы: уже не исходный текст, но ещё не машинный код конкретного процессора.
JIT (Just-In-Time compilation) – компиляция байт-кода в нативный машинный код во время выполнения, непосредственно перед тем как код понадобится; позволяет оптимизировать «горячие» (часто исполняемые) участки на лету, с учётом реальных данных выполнения.
	Компилятор переводит программу целиком и заранее → быстрый нативный исполняемый файл, ошибки ловятся раньше, но нет кроссплатформенности без перекомпиляции. Интерпретатор переводит и исполняет код по частям во время работы → медленнее, зато один код работает везде, где есть интерпретатор, а ошибки всплывают только во время выполнения. 
4. Управление памятью: сборка мусора и ручное управление.
Зачем вообще нужно управление памятью?
Во время работы программы постоянно создаются объекты. Все они занимают оперативную память (RAM). Если память не освобождать после использования, программа будет потреблять всё больше ресурсов, что приведёт к замедлению работы или завершению программы с ошибкой.
Поэтому возникает вопрос: Кто и когда должен освобождать память, которая больше не нужна?
Существует два основных подхода:
– ручное управление памятью;
– автоматическое управление памятью (GC)
Как устроена память программы
Упрощённо память процесса делится на две области:
– Stack (стек) - хранит локальные переменные и информацию о вызовах функций.
– Heap (куча) - зачастую используется для объектов, время жизни которых заранее неизвестно.
Именно куча требует управления памятью.
1. Ручное управление памятью
При ручном управлении программист сам отвечает за выделение и освобождение памяти.
Программа говорит компьютеру: "Выдели память."
а затем обязательно: "Теперь освободи её."
Пример (C++):
int* number = new int(5);
std::cout << *number;
delete number;
Возможные ошибки
Утечка памяти (Memory Leak)
Память выделена, но никогда не освобождена.
void foo() {
   int* p = new int(10);
}
После выхода из функции указатель исчезает, а память остаётся занятой. Если такая ситуация повторяется тысячи раз, программа начинает потреблять всё больше памяти.
Двойное освобождение (Double Free)
delete p;
delete p;
Освобождать одну и ту же память дважды нельзя. Это приводит к неопределенному поведению программы.
Висячий указатель (Dangling Pointer)
delete p;
std::cout << *p;
Память уже освобождена, но указатель всё ещё содержит старый адрес.
Плюсы ручного управления:
– максимальная производительность;
– полный контроль над использованием памяти;
– отсутствие пауз на работу сборщика мусора;
2. Автоматическое управление памятью (Garbage Collection)
При автоматическом управлении памятью программист создаёт объекты, а их удалением занимается сборщик мусора. Основной принцип: если на объект больше никто не ссылается, значит он больше не нужен и память можно освободить.
Пример (Java):
String text = new String("Hello");
text = null;
После того как переменная перестала ссылаться на объект "Hello", он становится кандидатом на удаление.
Как работает сборщик мусора
Существует множество алгоритмов GC, но общая идея одинакова.
Шаг 1. Поиск достижимых объектов
Сборщик начинает обход от объектов, которые ещё используются программой. Все найденные объекты считаются живыми.
Шаг 2. Поиск "мусора"
Если до объекта невозможно добраться ни по одной ссылке, значит он больше никому не нужен. Такой объект считается мусором.
Шаг 3. Освобождение памяти
Память, занимаемая мусором, освобождается и может использоваться повторно.
В языках со сборщиком мусора также могут происходить утечки памяти, но из-за неправильного хранения ссылок, а не из-за забытых “delete”.

5. Сравнение языков по основным характеристикам.
Языки различаются по нескольким независимым характеристикам, и по каждой приходится чем-то жертвовать ради другого. Свести сравнение к одному показателю, например к скорости, не выходит: выигрыш по одной оси почти всегда оплачивается проигрышем по другой.
Ключевые оси сравнения:
Парадигма - императивная, ООП, функциональная, логическая; большинство современных языков мультипарадигменны.
Дисциплина типизации - см. вопрос 2.
Управление памятью - ручное (C, C++), сборка мусора (Java, C#, Go, Python, JS), владение без сборщика (Rust), подсчёт ссылок и ARC (Swift), подсчёт ссылок с отдельным сборщиком циклов (CPython).
Модель выполнения - компиляция в нативный код (C, C++, Rust, Go), JIT поверх байткода (JVM, .NET, V8), интерпретация байткода (CPython, Ruby), транспиляция (TypeScript → JS).
Модель конкурентности - потоки и блокировки (C++, Java), CSP-каналы и горутины (Go), async/await (JS, C#, Rust, Python), акторы и «let it crash» (Erlang/Elixir). Отдельно - GIL: в референсной реализации CPython (и MRI Ruby) глобальная блокировка ограничивает параллелизм потоков CPU-bound кода (сейчас ведётся работа над опциональной сборкой без GIL).
Обработка ошибок - исключения (Java, C#, Python) против ошибок-как-значений (Result/Option в Rust, пара value, err в Go).

Как читать таблицу
Основные компромиссы, которые стоят за строками таблицы:
Контроль ↔ безопасность. C даёт полный контроль над памятью, перекладывая безопасность на программиста; Rust обеспечивает те же гарантии производительности с безопасностью памяти на компиляции — платой служит строгий borrow checker.
Продуктивность ↔ производительность. Python и Ruby ускоряют разработку и проигрывают в скорости; C++ и Rust наоборот. Часто это решается связкой: горячие участки на нативном языке, логика на скриптовом.
Простота ↔ выразительность. Go сознательно беден на возможности ради читаемости и командной работы; Scala и Haskell выразительнее, но требуют дисциплины.
Экосистема - зрелость библиотек, инструментов и рынок найма нередко перевешивают чисто технические характеристики.

Главная идея: язык выбирают под конкретную задачу и команду, взвешивая приемлемые компромиссы. Для сервиса с жёсткими требованиями к латентности, для быстрой проверки гипотезы и для системного кода с ручным управлением памятью рационально выбрать три разных языка — и это нормальный результат, а не признак того, что какой-то из них «хуже».

6. Типизация и безопасность в разных языках.
1. Статическая vs динамическая — КОГДА проверяются типы
Статическая — типы переменных известны и проверяются компилятором до запуска программы. Java, C#, Go — все три статически типизированы.
Динамическая — тип определяется и проверяется во время выполнения, у переменной нет фиксированного типа, есть только у значения (Python, JavaScript, PHP).
2. Строгая (сильная) vs слабая — НАСКОЛЬКО разрешены неявные преобразования


Строгая типизация — язык не допускает неявных преобразований между несовместимыми типами без явного указания программиста; операция с типами-нарушителями — ошибка. Java, C#, Go — все три строго типизированы.
Слабая типизация — язык сам неявно приводит типы друг к другу (классический пример — JavaScript: "5" + 3 === "53", "5" - 3 === 2).
3. Номинативная vs структурная типизация — совместимость типов по ИМЕНИ или по СТРУКТУРЕ
Это ключевое различие Go от Java/C#:
Номинативная типизация — Java и C#: тип A совместим с типом B, только если это явно объявлено (класс явно написал implements/: , или является наследником). Одинаковый набор методов без явного объявления родства не делает типы совместимыми.
Структурная типизация — Go: тип автоматически считается реализующим интерфейс, если обладает нужным набором методов, без всякого явного объявления (implements/: в Go просто не существует). Это проверяется компилятором статически (в отличие от Python, где duck typing проверяется в рантайме) — поэтому иногда точнее говорить «статическая структурная типизация».
4. Явная vs неявная типизация (вывод типов, type inference)
Не путать с динамической типизацией! Вывод типа (var в Java/C#, := в Go) – это по-прежнему статическая типизация: компилятор сам определяет и фиксирует тип переменной на этапе компиляции, просто программисту не нужно писать его руками. После вывода тип неизменен, как и при явном объявлении.
Типобезопасность (type safety) — гарантия того, что операция никогда не будет применена к данным несовместимого типа; нарушение либо не компилируется, либо предсказуемо и безопасно завершается управляемым исключением, а не неопределённым поведением (undefined behavior), как в C/C++.

Обобщения (Generics) используются как механизм типобезопасности. Их главная цель – ловить несовпадение типов на этапе компиляции, а не получать ClassCastException/InvalidCastException в рантайме от «универсальных» коллекций Object.
Java – стирание типов (type erasure): информация о параметре типа существует только на этапе компиляции и полностью удаляется из байт-кода; List<String> и List<Integer> в скомпилированном виде — это один и тот же List, компилятор лишь молча вставляет проверочные касты при чтении элементов. Следствия: нельзя написать new T(), нельзя сделать instanceof T, нельзя создать массив generic-типа напрямую, примитивы (int) в generics не допускаются вообще – приходится использовать обёртки (Integer) с автобоксингом.
C# – овеществлённые (reified) generics: информация о типе-параметре сохраняется в рантайме по-настоящему; List<int> и List<string> – действительно разные специализированные типы во время выполнения. 
Go – генерики появились только в 1.18 (2022): реализованы через частичную мономорфизацию (GCShape stenciling) – компромисс между полной генерацией отдельного кода под каждый тип (как в C++ шаблонах) и полным стиранием (как в Java): типы с одинаковой «формой» памяти (GC shape) могут переиспользовать один и тот же скомпилированный код.

7. Объектно-ориентированное программирование (ООП) в разных языках.
Объектно-ориентированное программирование (ООП) - это парадигма программирования, в которой программа организуется не как последовательность инструкций, работающих с общими данными, а как совокупность взаимодействующих объектов, каждый из которых объединяет в себе данные (состояние) и операции над этими данными (поведение).
1. Исторический контекст: почему возникло ООП
В 1960–70-е годы доминировало процедурное программирование (Fortran, ALGOL, C, Pascal). Программа представляла собой набор процедур (функций), которые обрабатывали данные, лежащие отдельно от них - в глобальных переменных или структурах, передаваемых по цепочке вызовов. Но с ростом систем до сотен тысяч строк проявились системные проблемы, получившие название «кризис программного обеспечения»:
Проблема 1. Данные и код, который с ними работает, разорваны. Структура Account (счёт) лежит в одном месте, а функции deposit(), withdraw(), printStatement() - где угодно в программе. Любая функция в любом модуле может изменить поле balance напрямую, минуя проверки. Инвариант данных («баланс не может быть отрицательным») невозможно гарантировать: он держится только на дисциплине программистов.
Проблема 2. Глобальное состояние и неконтролируемые зависимости. Когда сотни функций читают и пишут общие данные, изменение формата одной структуры требует найти и поправить все места использования. Компилятор в этом почти не помогает. Возникает «эффект ряби»: маленькая правка ломает код в неожиданных местах.
Проблема 3. Слабая поддержка повторного использования. Процедуру можно переиспользовать, но нельзя «слегка изменить» её поведение, не копируя код. Копипаста порождала дублирование, а дублирование - рассинхронизацию исправлений.
Проблема 4. Разрыв между моделью предметной области и кодом. Заказчик мыслит понятиями «счёт», «клиент», «заказ», а программа состоит из массивов, индексов и функций process_record_type_7(). Перевод требований в код и обратно требовал огромных интеллектуальных усилий и был источником ошибок.
Ключевая мысль: объединить данные и операции над ними в единую сущность, скрыть внутреннее устройство и позволить сущностям взаимодействовать только через явно объявленные интерфейсы. Это напрямую решает перечисленные проблемы:
– инвариант данных охраняется самим объектом (решение проблемы 1);
– зависимости идут через узкий публичный интерфейс, внутренности можно менять свободно (решение проблемы 2);
– наследование и полиморфизм позволяют расширять поведение без копирования кода (решение проблемы 3);
– объекты кода соответствуют сущностям предметной области: «счёт» в требованиях - это класс Account в коде (решение проблемы 4).
В 1980-е Бьярне Страуструп добавил классы к языку C - так родился C++, сделавший ООП массовым. В 1995 году появилась Java, в 2000-м - C#.
2. Базовые понятия ООП
2.1. Объект
Объект - это программная сущность, созданная на основе класса, которая инкапсулирует данные, описывающие её текущее состояние, и операции, определяющие её поведение. Объект самостоятельно отвечает за управление своим состоянием и взаимодействует с другими объектами через публичный интерфейс. Процесс создания экземпляра класса называется инстанцированием и обычно выполняется оператором new.
2.2. Класс
Класс - это описание (шаблон, чертёж) множества объектов с одинаковой структурой состояния и одинаковым поведением. Класс существует на этапе написания и компиляции программы; объекты существуют во время её выполнения.
2.3. Состояние объекта
Состояние - это значения всех полей объекта в конкретный момент времени. Состояние изменяется во времени: после вызова account.deposit(100) поле balance увеличилось - объект перешёл в новое состояние.
Важнейшее понятие, связанное с состоянием, - инвариант класса: условие, которое должно быть истинным для состояния любого корректного объекта в любой момент между вызовами его методов. Например: «баланс ≥ 0», «день месяца от 1 до 31». Одна из главных целей ООП - дать классу возможность гарантировать свои инварианты, не полагаясь на добросовестность внешнего кода. Именно для этого нужна инкапсуляция.
2.4. Поведение объекта
Поведение - это набор методов объекта, то есть операций, которые можно у него запросить. Ключевой сдвиг мышления по сравнению с процедурным стилем: мы не «вызываем функцию, передав ей данные», а «просим объект выполнить операцию над самим собой». Синтаксически это выражается записью object.method(args) вместо function(object, args). Внутри метода объект имеет доступ к собственному состоянию через неявную ссылку this.
Разница не только синтаксическая: раз операция принадлежит объекту, то какая именно операция выполнится, может зависеть от фактического типа объекта - это фундамент полиморфизма.
2.5. Взаимодействие объектов
Программа в ООП - это граф объектов, обменивающихся сообщениями. «Послать объекту сообщение» на практике означает «вызвать его публичный метод». Объект-отправитель знает только интерфейс получателя (какие методы у него можно вызвать), но не его внутреннее устройство.
Между объектами возможны отношения разной силы:
– ассоциация - объект знает о другом (хранит ссылку);
– агрегация - объект «имеет» другой, но не владеет его жизненным циклом (университет и преподаватели);
– композиция - объект владеет частью, и часть не существует без целого (дом и комнаты);
– наследование - объект «является» разновидностью другого.

3. Четыре принципа ООП
3.1. Инкапсуляция
Инкапсуляция - это (а) объединение данных и методов, работающих с этими данными, в единой сущности (классе) и (б) сокрытие внутреннего представления данных и деталей реализации от внешнего кода, с предоставлением доступа только через контролируемый публичный интерфейс.
Какую проблему решает. Главную проблему процедурного кода - невозможность гарантировать инварианты данных. Если поле balance публично, любой код в программе может записать туда -1000000, и найти виновника в большой системе почти невозможно. Второй эффект: раз внешний код не знает внутреннего представления, представление можно менять (например, заменить double на BigDecimal для денег), не ломая пользователей класса.
Различия между языками:
В Java инкапсуляция выражается парами методов getX()/setX() («геттеры/сеттеры»). Это соглашение, а не конструкция языка, поэтому код многословен.
В C# есть свойства (properties) - синтаксическая конструкция, которая снаружи выглядит как поле, но реализуется методами. Это делает код чище и позволяет, например, разрешить чтение всем, а запись - только самому классу (private set). Свойства - прямой урок, извлечённый из многословности Java.
В C++ есть три особенности. Во-первых, различие class/struct: в class члены по умолчанию private, в struct - public (наследие совместимости с C). Во-вторых, ключевое слово const у методов - дополнительный, отсутствующий в Java/C# уровень контроля: компилятор гарантирует, что метод не изменит состояние. В-третьих, механизм friend: класс может явно предоставить доступ к своим приватным членам конкретной внешней функции или классу - управляемое «пробитие» инкапсуляции, которого в Java/C# нет.

3.2. Наследование
Наследование - это механизм, позволяющий определить новый класс (производный, подкласс, наследник) на основе существующего (базового, суперкласса, родителя), при котором производный класс автоматически получает поля и методы базового и может добавлять новые члены и переопределять унаследованное поведение.
Какую проблему решает. Дублирование кода. В процедурном мире, если нужно поведение «почти как у существующей функции, но чуть иное», код копировали. Наследование даёт «программирование различиями»: общее пишется один раз в базовом классе, различия - в наследниках. Вторая, ещё более важная роль: наследование создаёт отношение подтипа - везде, где ожидается Animal, можно передать Dog (принцип подстановки Лисков). Без этого невозможен полиморфизм.
Пример на Java:
public class Animal {
   protected String name;              // доступно наследникам


   public Animal(String name) { this.name = name; }


   public void eat() {
       System.out.println(name + " ест");
   }
}


public class Dog extends Animal {       // extends — единственный способ, один родитель
   public Dog(String name) {
       super(name);                     // вызов конструктора родителя — первой строкой
   }


   public void bark() {                 // новое поведение
       System.out.println(name + " лает");
   }
}


// Использование:
Dog d = new Dog("Рекс");
d.eat();    // унаследовано
d.bark();   // собственное
Animal a = d;   // подстановка: Dog является Animal
Различия между языками:
– Java и C# допускают только одиночное наследование классов (один прямой родитель), компенсируя это возможностью реализовать много интерфейсов. Все классы неявно наследуют от корневого Object (System.Object в C#).
– C++ поддерживает множественное наследование классов и не имеет единого корневого класса. Кроме того, в C++ у наследования есть режимы: public (is-a, обычный случай), protected и private (наследование реализации, снаружи отношение подтипа не видно) - Java и C# такого различия не имеют, у них наследование всегда «публичное».
– В Java конструктор родителя вызывается через super(...), в C# - через : base(...), в C++ - через список инициализации : Animal(...).

3.3. Полиморфизм
Полиморфизм - это возможность единообразно работать с объектами разных типов через общий интерфейс, при которой фактически выполняемая операция определяется реальным (динамическим) типом объекта, а не типом ссылки/указателя, через который к нему обращаются. Различают
полиморфизм подтипов (динамический, времени выполнения) - через виртуальные методы и переопределение; это «главный» полиморфизм ООП;
параметрический полиморфизм - обобщённое программирование (generics в Java/C#, шаблоны в C++);
ad hoc полиморфизм - перегрузка функций и операторов
Простыми словами. Вы говорите объекту «нарисуйся» — и круг рисуется как круг, а квадрат как квадрат, хотя вызывающий код одинаков и вообще не знает, с кем говорит. Одно сообщение - много форм ответа.
Пример на Java:
public abstract class Shape {
   public abstract double area();
}


public class Circle extends Shape {
   private final double r;
   public Circle(double r) { this.r = r; }


   @Override
   public double area() { return Math.PI * r * r; }
}


public class Square extends Shape {
   private final double side;
   public Square(double side) { this.side = side; }


   @Override
   public double area() { return side * side; }
}


// Полиморфный код — не знает о конкретных фигурах:
public static double totalArea(List<Shape> shapes) {
   double sum = 0;
   for (Shape s : shapes) sum += s.area();
   return sum;
}
В Java все нестатические методы виртуальны по умолчанию - ключевое слово virtual не нужно. В C# методы не виртуальны по умолчанию: чтобы метод можно было переопределить, его надо пометить virtual (или abstract), а переопределение - обязательно словом override.
Виртуальный метод - это метод, для которого конкретная реализация выбирается не во время компиляции, а во время выполнения программы (runtime) в зависимости от реального типа объекта.
Различия между языками:
– Полиморфизм и память. В Java и C# полиморфизм работает «сам собой», потому что объекты всегда доступны по ссылке. В C++ полиморфизм работает только через указатель или ссылку;
– Перегрузка операторов: есть в C++ и C#, отсутствует в Java (авторы Java сочли её источником злоупотреблений).

3.4. Абстракция
Абстракция - это выделение существенных характеристик сущности, значимых для решаемой задачи, и игнорирование несущественных; в коде - определение контракта (что делает сущность) отдельно от реализации (как она это делает). Инструменты абстракции - абстрактные классы и интерфейсы.
Какую проблему решает. Сложность. Человек не может держать в голове миллионы строк; абстракция позволяет думать о системе слоями.
Отметим связь принципов: абстракция определяет, что показать; инкапсуляция - как спрятать остальное; полиморфизм оживляет абстракцию, подставляя за контрактом разные реализации; наследование - один из способов эти реализации связать с контрактом.
Различия между языками:
– Java и C# имеют интерфейс как отдельную языковую конструкцию, семантически отличную от класса. 
– C++ отдельной конструкции не имеет: «интерфейс» - это класс, состоящий только из чисто виртуальных функций. Благодаря множественному наследованию нужды в отдельной конструкции нет.

8. Функциональное программирование в разных языках.
Языки поддерживают функциональный стиль в очень разной степени. Писать функционально можно почти везде; вопрос в том, что язык гарантирует и поощряет по умолчанию - чистоту, неизменяемость, ленивость, оптимизацию хвостовой рекурсии, управление эффектами.
Ключевые понятия:
Функции первого класса - их можно передавать, возвращать и хранить; на этом строятся функции высшего порядка.
Чистые функции и ссылочная прозрачность - функция без побочных эффектов, вызов которой можно заменить её результатом без изменения поведения программы.
Неизменяемость - данные не меняются на месте; вместо этого создаются новые значения (часто через персистентные структуры данных).
Декларативность - описывается «что» вычислить, а не «как»; циклы вытесняются рекурсией и композицией.
Продвинутый инструментарий - замыкания, каррирование и частичное применение, ленивые вычисления, алгебраические типы данных (ADT) и сопоставление с образцом, классы типов, функторы и монады как способ структурировать вычисления и эффекты.

Спектр языков
Чисто функциональные - Haskell (ленивый по умолчанию, чистота принудительна через тип IO и монады), Elm, PureScript.
Семейство ML - OCaml, F#, Standard ML: энергичные, допускают эффекты, но с мощным выводом типов, ADT и pattern matching (OCaml 5 добавил алгебраические эффекты).
Семейство Lisp - Clojure на JVM с неизменяемыми персистентными структурами по умолчанию и макросами, а также Scheme и Racket.
Функциональные с акторами - Erlang/Elixir на BEAM: неизменяемость и чистые функции плюс модель процессов-акторов, дающая отказоустойчивость.
Гибриды и мультипарадигменные - Scala (ООП + ФП на JVM); JavaScript, Python, Java (Stream, Optional), C# (LINQ), Kotlin, Rust (enum как ADT, match, Option/Result) - инструменты ФП поверх иной основы.

Практическая ценность
	Идеи ФП полезны и вне «чистых» языков. Чистые функции повышают тестируемость (детерминированность, отсутствие скрытого состояния), неизменяемость упрощает безопасность конкурентного кода (нет гонок за общими данными), а функции высшего порядка и композиция улучшают локальность рассуждений. Именно поэтому эти идеи проникли в мейнстрим: Stream в Java, LINQ в C#, иммутабельные структуры во фронтенде.
Главная идея: «поддерживает ФП» и «функциональный язык» - разные вещи. Наличие map, filter и лямбд ещё не делает язык функциональным; решают гарантии — чистота, неизменяемость по умолчанию, ленивость, оптимизация хвостовых вызовов и модель эффектов. При этом сами приёмы ФП стоит применять в любом языке: они дают тестируемость и безопасность конкурентного кода.

9. Управление памятью в разных языках.
Стек (stack) – область памяти для локальных переменных и кадров вызова функций (call frame). Работает по принципу LIFO, выделение/освобождение автоматическое и мгновенное (просто сдвиг указателя стека при входе/выходе из функции), размер ограничен и известен заранее. Данные в стеке живут ровно столько, сколько выполняется функция.
Куча (heap) – область для динамически создаваемых данных, размер которых заранее не известен или которые должны пережить вызвавшую их функцию. Выделение дороже стека, освобождение либо ручное, либо через сборщик мусора.
Значимые (value) и ссылочные (reference) типы, где что физически лежит?
Три языка ведут себя по-разному:
Java: примитивы (int, double, boolean и т.д.) — значимые типы, хранятся в стеке, если это локальная переменная, либо непосредственно внутри объекта, если это поле. Все объекты (включая обёртки Integer, String, массивы) — ссылочные типы и всегда создаются в куче; в стеке лежит только ссылка на них. 
C#: язык явно различает struct (значимый тип) и class (ссылочный тип) на уровне синтаксиса. Значимый тип как локальная переменная лежит в стеке; как поле объекта или элемент массива — лежит внутри этого объекта/массива в куче (без отдельного выделения памяти под каждый элемент). Ссылочный тип — сам объект всегда в куче, в стеке — только ссылка.
Go: формально нет деления на «класс» и «структуру» с разной семантикой хранения, как в C# — вместо этого работает escape-анализ (escape analysis): компилятор во время компиляции определяет, «убегает» ли адрес переменной за пределы функции (например, возвращается как указатель, сохраняется в глобальной переменной, захватывается замыканием). Если не убегает — переменная размещается в стеке, даже если это структура; если убегает — компилятор автоматически размещает её в куче. Это происходит незаметно для программиста и является отличительной чертой Go по сравнению с Java/C#, где решение стек/куча жёстче привязано к самому определению типа (class vs struct, примитив vs объект).
10. Многопоточность и асинхронность в разных языках.
Классическая модель «один запрос - один поток ОС» упирается в стоимость потоков: каждый поток ОС требует стека (обычно 1–8 МБ виртуальной памяти), а переключение контекста выполняется ядром и стоит микросекунды. Обслуживание десятков тысяч соединений таким способом невозможно (проблема C10K). Поэтому языки эволюционировали в двух направлениях: одни предоставляют лёгкие пользовательские потоки, мультиплексируемые поверх потоков ОС (Go, Kotlin, современная Java), другие - событийную модель с явной асинхронностью через futures/promises и синтаксис async/await (JavaScript, C#, отчасти C++ и Kotlin).
Вторая фундаментальная проблема, которую должен решать язык, - это безопасность разделяемого состояния: гонки данных, взаимные блокировки, видимость изменений между потоками. Разные языки отвечают на неё по-разному: формальной моделью памяти и примитивами синхронизации (Java, C++), идеологией обмена сообщениями вместо разделения памяти (Go, каналы), либо полным устранением разделяемой изменяемой памяти между потоками (JavaScript).
1. Java: потоки ОС, формальная модель памяти и эволюция к виртуальным потокам
1.1. Базовая модель: класс Thread
Класс java.lang.Thread является тонкой обёрткой над потоком операционной системы (модель 1:1). Создание потока - дорогая операция, поэтому прямое использование new Thread() в промышленном коде считается антипаттерном; вместо этого применяются пулы потоков.
Ключевые языковые примитивы синхронизации встроены в сам язык:
ключевое слово synchronized - каждый объект в Java имеет встроенный монитор (mutex + condition variable), методы wait()/notify()/notifyAll() определены в Object;
ключевое слово volatile - гарантирует видимость записей между потоками и запрещает переупорядочивание. (работает только с примитивами и ссылками на объекты, но не с содержимым)
1.2. java.util.concurrent
– ExecutorService и пулы потоков (ThreadPoolExecutor, ScheduledThreadPoolExecutor) - отделили задачу (Runnable, Callable) от механизма исполнения;
– ForkJoinPool (Java 7) - пул с алгоритмом work-stealing для рекурсивно-параллельных задач; на нём же основаны параллельные стримы (stream().parallel(), Java 8);
– конкурентные коллекции (ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue);
– явные блокировки (ReentrantLock, ReadWriteLock, StampedLock), синхронизаторы (CountDownLatch, Semaphore, CyclicBarrier, Phaser);
– атомарные классы (AtomicInteger, AtomicReference) поверх CAS-инструкций процессора - основа неблокирующих (lock-free) алгоритмов.
1.3. Асинхронность: CompletableFuture
– CompletableFuture (Java 8) - реализация модели promise: композиция асинхронных операций через thenApply, thenCompose, thenCombine, exceptionally. Недостаток - «callback-подобный» стиль: цепочки комбинаторов хуже читаются, чем линейный код, стек-трейсы разорваны, а async/await в язык так и не был добавлен - вместо него Java пошла другим путём.
1.4. Виртуальные потоки (Java 21)
Виртуальные потоки - лёгкие потоки, управляемые JVM, мультиплексируемые на небольшое число потоков-носителей ОС (модель M:N). При блокирующем вызове (сокет, sleep) виртуальный поток «размонтируется» с носителя, освобождая его. Стек виртуального потока хранится в куче и растёт динамически, стоимость создания - сотни байт вместо мегабайт. Это позволяет вернуться к простому императивному стилю «поток на запрос» при масштабируемости событийной модели.
2. Go: горутины, CSP и «не общайтесь через разделяемую память»
2.1. Горутины и планировщик GMP
Горутина - сверхлёгкий пользовательский поток: запуск одним ключевым словом go f(), начальный стек ~2–8 КБ, растущий и сжимающийся динамически. Рантайм Go содержит собственный планировщик по схеме G-M-P (Goroutine - Machine/поток ОС - Processor/логический процессор): горутины мультиплексируются на пул потоков ОС. Начиная с Go 1.14 планировщик вытесняющий, что исключает захват процессора одной горутиной в тесном цикле.
 В Go нет и не нужен async/await - это осознанное концептуальное решение: отсутствует деление функций на «цветные» (синхронные/асинхронные), от которого страдают JS и Kotlin.
2.2. Каналы
Канал (chan T) - типизированный примитив передачи данных между горутинами, бывают небуферизованные и буферизованные.
Идиоматические паттерны: worker pool, fan-in/fan-out, pipeline. Отмена и дедлайны стандартизованы через context.Context, пронизывающий все API.
2.3. Классическая синхронизация и инструменты
Разделяемая память не запрещена: пакет sync даёт Mutex, RWMutex, WaitGroup, Once, sync/atomic.
3. C++: максимальный контроль, стандартизированная модель памяти и корутины без рантайма
До 2011 года стандарт C++ вообще не знал о потоках — использовались POSIX threads, WinAPI, OpenMP. C++11 стандартизировал многопоточность на уровне языка и библиотеки.
3.1. std::thread и модель памяти C++11
std::thread - обёртка над потоком ОС (1:1) без пула и планировщика: язык даёт ровно то, что даёт ОС. Стандарт C++11 ввёл формальную модель памяти (развитие идей JMM): понятие гонки данных как неопределённого поведения (UB), атомарные типы std::atomic<T> с настраиваемыми порядками согласования (memory_order_relaxed, acquire/release, seq_cst). Это уникальная черта C++: программист может явно выбирать компромисс между строгостью гарантий и производительностью вплоть до отдельных барьеров памяти - ни один другой рассматриваемый язык такого уровня контроля не даёт.
3.2. Библиотечные примитивы
– мьютексы (std::mutex, recursive_mutex, shared_mutex — C++17) и RAII-обёртки (lock_guard, unique_lock, scoped_lock с алгоритмом избежания дедлоков);
– std::condition_variable;
– futures/promises: std::future, std::promise, std::packaged_task, std::async (высокоуровневый запуск задачи; на практике критикуется за неопределённость политики запуска и блокирующий деструктор);
– C++20: std::jthread (joining thread + кооперативная отмена через stop_token), std::latch, std::barrier, std::counting_semaphore, std::atomic::wait/notify;
– C++17: параллельные алгоритмы STL (std::sort(std::execution::par, ...)).
Существенный пробел стандарта - отсутствие стандартного пула потоков и исполнителей.
3.3. Корутины C++20
C++20 ввёл stackless-корутины как языковой механизм: co_await, co_yield, co_return. Концептуальная особенность — это каркас без батареек: язык определяет лишь протокол трансформации функции в конечный автомат (promise_type, awaiter), а типы задач, планировщики и event loop должен предоставить программист или библиотека (Asio, cppcoro, libunifex). Это даёт нулевые накладные расходы и полную настраиваемость, но делает порог входа самым высоким среди всех языков.
4. JavaScript: однопоточный event loop и асинхронность как единственная модель
Модель исполнения - цикл событий: очередь макрозадач (таймеры, IO-колбэки) и очередь микрозадач (продолжения промисов), обрабатываемые до опустошения между макрозадачами. Все операции ввода-вывода неблокирующие и делегируются среде исполнения
JavaScript концептуально противоположен предыдущим языкам: исполнение пользовательского кода однопоточно, и конкурентность достигается исключительно асинхронностью.
Следствия модели: отсутствие гонок данных и необходимости в мьютексах по построению (код между точками ожидания атомарен относительно другого JS-кода); цена - любая долгая CPU-bound операция блокирует весь цикл событий и «замораживает» приложение.
5. Kotlin: корутины, suspend-функции и структурированная конкурентность
5.1. suspend-функции
Ключевое слово suspend помечает функцию, способную приостанавливаться без блокировки потока. В отличие от JS, await не нужен как отдельный оператор — вызов suspend-функции выглядит как обычный вызов, что делает асинхронный код внешне неотличимым от синхронного. Плата - «цветные функции»: suspend-функцию можно вызвать только из корутины.
5.2. Структурированная конкурентность
Kotlin - язык, который ввёл structured concurrency в мейнстрим: каждая корутина запускается в CoroutineScope, образуя дерево «родитель–потомки». Родитель не завершается раньше детей; отмена (Job.cancel()) распространяется по дереву кооперативно; исключение потомка по умолчанию отменяет всё дерево (кроме SupervisorJob). Это системно решает проблемы утечек фоновых задач и «осиротевших» операций
Строители корутин: launch (fire-and-forget → Job), async (значение → Deferred<T>, ожидание через await()), runBlocking (мост в блокирующий мир). Диспетчеры управляют пулами потоков: Dispatchers.Default (CPU-bound), Dispatchers.IO (эластичный пул для блокирующего IO), Dispatchers.Main (UI-поток Android); переключение - withContext.
5.3. Каналы и Flow
Kotlin заимствует у Go каналы (Channel<T>, select) для горячих потоков данных и добавляет Flow - холодные асинхронные потоки в духе реактивного программирования.

Удобство написания и сложность изучения.
Минимальную концептуальную нагрузку даёт Go: одна модель (горутины + каналы), синхронный стиль без «цветных функций». Kotlin удобен, но требует освоить контексты, диспетчеры, кооперативную отмену. Java исторически многослойна (Thread → Executors → CompletableFuture → virtual threads), что усложняет изучение, хотя каждый слой в отдельности логичен. C++ требует понимания модели памяти на уровне «железа» .
Контроль против автоматизации.
Это главная ось сравнения. C++ - максимум контроля (вплоть до порядков атомарных операций и привязки потоков к ядрам) и нулевая автоматизация. Go - противоположный полюс: планировщик и интеграция с IO полностью скрыты, программисту почти нечего настраивать. Java и Kotlin занимают середину: высокоуровневые абстракции по умолчанию, но при необходимости доступен тонкий тюнинг пулов и JVM. 
Производительность и масштабируемость.
Для CPU-bound задач порядок примерно таков: C++ > Java/Kotlin (JIT) ≈ Go (проигрывает JVM в пиковой оптимизации, выигрывает в предсказуемости и потреблении памяти). Для IO-bound конкурентности решающим является не язык, а модель: миллионы лёгких задач доступны Go, Kotlin и современной Java. Классический C++ требует событийных библиотек (Asio) для сравнимого результата.
Стоимость создания потоков. 
Иерархия: поток ОС (C++, классическая Java) - мегабайты стека и системный вызов; горутина/корутина/виртуальный поток (Go, Kotlin, Java 21) - килобайты и байты, создание в пользовательском пространстве за наносекунды

Сильные и слабые стороны моделей и типичные области применения
Java
Сильные стороны: эталонная библиотека java.util.concurrent; формальная и проверенная временем модель памяти; виртуальные потоки объединили простоту блокирующего стиля с масштабируемостью событийного; зрелые инструменты диагностики.
Слабые стороны: историческая многослойность API; многословность; накладные расходы JVM и GC-паузы.
Типичные области применения: корпоративные и банковские бэкенды, высоконагруженные микросервисы, big-data-платформы.
Go
Сильные стороны: минимальная концептуальная сложность; сверхдешёвые горутины и прозрачная интеграция с неблокирующим IO; каналы и select как выразительная идиоматика; отсутствие «цветных функций»; race detector; быстрая компиляция в единый бинарник.
Слабые стороны: слабый контроль над планировщиком; утечки горутин и дедлоки на каналах не предотвращаются; нет приоритетов задач; для CPU-критичных участков уступает C++ и JIT-компилируемой JVM.
Типичные области применения: облачная инфраструктура и DevOps-инструменты, сетевые сервисы, API-шлюзы, прокси и балансировщики, CLI-утилиты, микросервисы.
C++
Сильные стороны: максимальная производительность и предсказуемость; полный контроль над памятью, атомарными операциями, привязкой к ядрам; стандартизованная модель памяти с настраиваемыми порядками согласования; корутины с нулевыми накладными расходами; пригодность для систем реального времени.
Слабые стороны: наивысшая сложность и высокая цена ошибки; отсутствие в стандарте пула потоков и исполнителей (до C++26); корутины - «каркас без батареек»; долгий цикл разработки; безопасность целиком на программисте и санитайзерах.
Типичные области применения: системное ПО, операционные системы и драйверы, СУБД и движки хранения, игровые движки, HFT и биржевые системы, рендеринг и HPC, встраиваемые системы, браузеры и рантаймы других языков.
Kotlin
Сильные стороны: лучшая в классе эргономика корутин (suspend без явного await); структурированная конкурентность как норма языка — системное решение проблем отмены и утечек; Flow для реактивных потоков с backpressure; полная совместимость с Java-экосистемой; мультиплатформенность.
Слабые стороны: «цветные функции» (suspend делит мир на два); зависимость от внешней библиотеки kotlinx.coroutines; необходимость понимать контексты, диспетчеры и семантику отмены; гонки данных при разделяемом состоянии не исключаются; отладочные стек-трейсы корутин сложнее потоковых.
Типичные области применения: Android (официальный язык; корутины - стандарт асинхронности UI), серверная разработка (Ktor, Spring WebFlux + корутины), мультиплатформенные мобильные приложения (KMP).
